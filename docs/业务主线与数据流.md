> 来源：课程文档 1.1 / 1.3 / 6.1 / 6.3 / 15.3 + 源码实证核对

## 一、这个项目在业务上到底解决什么

### 痛点（不是"没有信息"，而是"信息太多且太散"）

一个 PR 能不能合，需要同时看四处：

```
GitHub Diff  →  改了哪些文件、有没有风险
Actions 日志 →  CI 过没过、为什么失败
Issue 列表   →  这个改动是为谁、为什么做的
群聊/文档    →  之前有没有讨论过、有没有约定
```

这些信息散落在不同系统，**Commiter（代码合并人）变成了"人肉路由器"**：手工拼凑、容易遗漏、难以追溯、质量依赖个人经验。

直接把材料丢给大模型也不行：
- 上下文有上限，材料多了直接报错
- 材料还是得有人先去找、去筛、去整理

### DevFlow AI 的定位

**不是一个问答机器人，而是一个"会使用工具的助手"。**

它能像资深工程师那样：**自动串联 Issue / PR / CI / 日志 → 拼出完整上下文 → 分析风险 → 给出明确建议**，并且**留下可追溯的过程**。

### 一句话业务价值

> 把"人肉查资料 + 凭经验判断"变成"系统自动取证 + 基于证据判断 + 过程可复盘"。

## 二、业务主线：四个动作

用户问「最新 PR 能不能合并？」时，系统不是"生成答案"，而是走完四步：

| 步骤 | 业务含义 | 如果缺了会怎样 |
|---|---|---|
| **① 定位** | 先确认"哪个仓库、哪个会话" | 「最新」「这个」「之前那个」全都失去意义 |
| **② 取证** | 查 PR / CI / Issue / 历史证据 | 变成拍脑袋，答案没有依据 |
| **③ 判断** | 简单问题调一个工具；复杂问题交给多 Agent 分工 | 复杂问题被一个 Agent 硬扛，过程黑盒、结果不可复盘 |
| **④ 沉淀** | 保存消息、运行记录、工具轨迹、引用证据 | 下次对话接不上、出错无法定位、效果无法评测 |

**记住这四个词，就能看懂每个模块在业务链上的位置。**

## 三、五层架构与职责

课程的原话：**上层负责交互，中层负责调度和判断，下层负责证据与记忆。**

| 层 | 职责 | 本项目对应 | 关键代码 |
|---|---|---|---|
| **① 用户层** | 用户能看到、能操作的地方 | Next.js 页面（Chat / 仓库 / Issue / PR / CI / 周报 / 评测） | `frontend/app/` |
| **② 应用服务层** | 业务"交通枢纽"：接请求、定位仓库与会话、流式返回、保存结果、记录轨迹 | 18 个路由模块 | `api/routes/` |
| **③ 智能协作层** | ChatAgent 主控 + 专用 Agent + 多 Agent 工作流 + Skill 注册中心 | Agent 编排 | `services/agents/`、`services/skills/` |
| **④ 知识与工具层** | 给 Agent 提供"手和眼睛"：RAG / Memory / Workspace / GitHub / LLM | 检索与工具 | `services/rag/`、`services/chat_memory.py`、`services/github/`、`services/llm/` |
| **⑤ 数据基础层** | 把事实、会话、运行记录、轨迹存下来 | PostgreSQL + Milvus + 本地文件 | `db/`、`services/rag/vector_store.py` |

**依赖方向**：① → ② → ③ → ④ → ⑤，**下层永远不 import 上层**。

## 四、七条数据流（逐条可追踪）

这是你最需要的部分。每条流都标注了：**起点 → 经过的文件 → 终点 → 触发方式**。

### 流 1：GitHub 事实 → 本地快照（同步）

```
触发：连接仓库 / 手动刷新 / 定时任务(300s) / Webhook
  ↓
api/routes/repos.py 或 webhooks.py 或 services/scheduler.py
  ↓
services/repos_sync.py  ← 【同步核心，唯一规则】
  ↓  调用
services/github/client.py → issues.py / pull_requests.py / actions.py
  ↓  访问
GitHub REST API
  ↓  返回 JSON
services/repos_sync.py  ← 映射成内部模型（幂等 upsert）
  ↓
PostgreSQL: repositories / issues / pull_requests / pr_files
            / pr_review_comments / workflow_runs
  ↓  更新
repositories.last_sync_at
```

**业务规则**：同一个 GitHub 对象同步多次，本地只留一行，内容以最新为准。
**下游消费者**：只读接口（`api/routes/issues.py` 等）、RAG 入库（`services/rag/indexing.py`）、Agent 工具。

### 流 2：仓库代码 → 代码图谱

```
触发：连接仓库后的后台任务 / 手动重建
  ↓
services/code_analysis.py  ← git clone / 更新 checkout
  ↓  用 AST 解析
PostgreSQL: code_symbols / code_relations
  ↓
api/routes/code_graph.py  →  前端代码图谱页
```

**业务意义**：回答"这个函数被谁调用""改这个文件会影响什么"。

### 流 3：文档与研发事实 → 向量库（RAG 入库）

```
触发：用户上传文档 / 仓库数据索引 / 周报生成
  ↓
api/routes/rag.py（返回 202）或 services/rag/indexing.py
  ↓  后台任务
services/rag/document_processing.py  ← 状态机编排
  ↓
document_extraction.py  → 解析 PDF/DOCX/MD/JSON/CSV
  ↓
chunking.py  → 结构感知切片（父子块）
  ↓
embeddings.py  → 向量化（1024 维）
  ↓
vector_store.py  → 双写
  ↓
PostgreSQL: documents（全文，事实源） + Milvus（向量，索引副本）
```

**业务规则**：`source_policy.py` 决定哪些进 RAG —— **代码文件被明确排除**。

### 流 4：用户问题 → 带引用的回答（RAG 查询 + Agent）

```
用户提问（前端 askAgent）
  ↓
api/routes/chat.py
  ├ ① ProgressiveContextManager.ensure_headroom()  → 压缩旧上下文
  ├ ② MessageStore.append(role="user")             → 存消息
  ├ ③ ContextAssembler.assemble()                  → 组装上下文
  └ ④ _build_conversation_tools(db)                → 注入 14 个工具
  ↓
services/agents/chat_agent.py  ← LangGraph 工具循环（最多 12 步）
  ├ 调 rag.search_similar_documents
  │    ↓
  │  services/rag/knowledge_base.py → retrieval.py（向量+BM25 融合）
  │    → rerank.py → answer_gate.py（证据够不够？）
  │    → qa.py（组装 prompt → LLM → 带引用回答）
  ├ 或调 issue_agent / pr_review_agent / ci_debug_agent
  ├ 或调 workflow.run_engineering_review（多 Agent）
  └ 或读工作区代码 workspace.read_file / search_code
  ↓
SSE 流式返回（thought / tool_use / tool_result / delta / final）
  ↓
落库：ChatMessage + AgentRun + SessionSealer.seal()
```

### 流 5：对话 → 长期记忆

```
一轮对话结束（收到 final 事件）
  ↓
services/chat_memory.py → SessionSealer.seal()
  ↓  提炼
PostgreSQL: conversation_memories（会话级）
            thread_memories（仓库级）
            memory_candidates（待人工审核的候选）
  ↓  人工 approve（api/routes/knowledge.py）
documents（进 RAG，可被检索）
```

**业务规则**：记忆不是自动生效的，重要事实要**人工批准**才晋升为长期知识。

### 流 6：上下文 → 压缩（token 预算）

```
每轮请求前
  ↓
services/context_compression.py
  ├ estimate_tokens()           → 粗估 token
  ├ calculate_context_pressure()→ 算压力等级
  └ compress_messages()         → 按预算压缩
  ↓
services/chat_memory.py → ProgressiveContextManager
  ├ 微压缩（microcompact）      → 保留最近 N 条
  ├ 插入 compaction boundary    → 记录"压缩起点"
  └ 摘要沉淀                    → 结论进记忆
```

**业务规则**：压缩不是"删除历史"，而是"整理成更适合继续工作的形态"。

### 流 7：AI 写操作 → 草稿 → 人工确认 → GitHub

```
Agent 判断需要改 GitHub（关 Issue / 加标签 / 评论）
  ↓
services/agents/safety_agent.py  → 判风险等级
  ↓
PostgreSQL: action_drafts（status=pending_confirmation）
  ↓  人工在页面点"确认"
api/routes/action_drafts.py
  ↓
services/github/client.py  → POST / PATCH
  ↓
GitHub
  ↓
PostgreSQL: action_drafts.execution_result + audit_logs
```

**业务规则**：**AI 永远不能直接写 GitHub**。必须经过"草稿 → 人工确认 → 执行 → 审计"。

## 五、数据分流规则（什么数据走哪条路）

这是最容易搞混的地方。**不是所有数据都进 RAG。**

| 数据类型 | 走哪条路 | 为什么 |
|---|---|---|
| **源码** | 工作区实时读取（`workspace.read_file` / `search_code`） | 代码天天变，向量索引会过期 → 给出错误答案 |
| **Issue / PR / CI 状态字段** | 直接查 PostgreSQL | 结构化数据，SQL 精确查询比语义检索准 |
| **Issue 正文 / PR 说明与 Review / 失败 CI 日志** | 进 RAG | 非结构化长文本，需要语义召回 |
| **项目文档 / 上传知识 / 已批准的长期记忆** | 进 RAG | 稳定知识，会反复被检索 |
| **会话历史** | 记忆系统按会话范围读（`chat_memory.py`） | 有明确的会话边界，不需要全局语义检索 |
| **团队成员 / 周报** | 直接查数据库 | 派生数据，实时计算 |

**判断标准**：**需要"跨来源语义召回 + 反复使用"的非结构化知识 → 进 RAG；其余走直查或工作区。**

## 六、注释里的业务标注规范

从第 2 批开始，每个文件的头部注释统一加三个业务字段：

```python
"""
<模块名>
========

【业务定位】
    用一句人话说明：这个模块在业务上解决什么问题。
    不要写"处理 XXX 逻辑"，要写"因为业务上需要 XXX，所以这里负责 XXX"。

【数据流向】
    上游：谁把数据交给它（文件路径）
    下游：它把数据交给谁（文件路径 / 表名）

【核心业务规则】
    一句话概括这个模块必须遵守的业务约束。
    例如"同一对象同步多次只留一行""AI 不能直接写 GitHub"。

【技术要点】
    实现上的关键设计（可选，复杂模块才写）
"""
```

**行内注释同样要带业务视角**，例如：

```python
# 【业务】为什么要按 repo_id + github_issue_id 双条件查：
#   只按 issue_id 查，两个仓库都有 #42 时会串线（拿到别的项目的数据）。
#   这是"仓库隔离"业务规则的代码落点。
```

## 七、追数据流的推荐顺序

想完整走一遍数据流，按这个顺序读代码：

| 顺序 | 读什么 | 能看到什么流 |
|---|---|---|
| 1 | `main.py` → `core/config.py` → `db/session.py` | 系统怎么起来、连哪个库 |
| 2 | `api/routes/repos.py` → `services/repos_sync.py` → `services/github/*` | **流 1**（同步） |
| 3 | `db/models.py` | 数据最终长什么样 |
| 4 | `api/routes/chat.py` → `services/agents/chat_agent.py` | **流 4 前半**（定位+调度） |
| 5 | `services/rag/knowledge_base.py` → `retrieval.py` → `qa.py` | **流 4 后半**（取证+回答） |
| 6 | `services/rag/document_processing.py` → `chunking.py` → `vector_store.py` | **流 3**（入库） |
| 7 | `services/chat_memory.py` → `context_compression.py` | **流 5、6**（记忆+压缩） |
| 8 | `services/agents/safety_agent.py` → `api/routes/action_drafts.py` | **流 7**（安全写操作） |

## 八、一句话总纲

> 用户提出问题 → 系统定位上下文 → RAG 和工具负责取证 → ChatAgent 负责调度 → 专用 Agent 负责专项分析 → 多 Agent 工作流负责复杂判断 → 最后把过程沉淀成记忆、记录和评测数据。
