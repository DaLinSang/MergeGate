## 1. 主推版：投后端 / AI 应用开发

> 直接复制。四段结构对齐 16.2 的"写法 1"，但内容按你的实现重写。

### DevFlow AI 研发协作 Agent 平台

**项目介绍**

面向 GitHub 研发协作场景的全栈 AI Agent 系统。将 Issue、PR、Review、CI 日志、项目文档与本地代码统一接入，提供 Issue 分诊、PR 审查、CI 排障、带引用问答和工程周报；涉及评论、打标签、关闭 Issue 等外部写操作时，先生成操作草稿，经权限校验与人工确认后才调用 GitHub API。

**技术栈**

Python、FastAPI、Pydantic、SQLAlchemy 2.0、PostgreSQL（pgvector）、LangChain、LangGraph、Milvus、MCP、SSE、Next.js、TypeScript、Docker Compose

**个人职责**

- **研发数据底座：** 对接 GitHub REST API 同步 Issue、PR、Review、Workflow Run、Job 与失败日志，按 `repo_id` 做数据隔离、按 GitHub ID 幂等 upsert，累计落库 32 张表、对外提供 104 个 HTTP 接口；接入本地工作区文件读取与代码搜索，作为 Agent 判断"当前代码长什么样"的事实源。
- **Agent 架构：** 基于 LangGraph 与原生 Tool Calling 实现 ChatAgent 推理循环（14 个工具、单轮最多 12 步），设计重复调用检测、步数预算、错误分类重试三道刹车，避免 Agent 空转与成本失控；将 Issue 分诊、PR 审查、CI 排障拆为专用 Agent，跨领域问题由 Planner → 专用 Agent → Observer → Synthesis 编排。
- **RAG 与上下文工程：** 实现多格式文档解析、结构感知切片（父子块）、向量与 BM25 混合召回（0.62 / 0.30 加权融合、双路命中加成）、Rerank 与编号引用，并按 `repo_id` 与来源类型隔离；上下文按"最近消息 / 历史摘要 / 长期记忆 / 本轮检索证据"分层组装，依据 Token 压力触发两级压缩，保证长对话不丢关键事实。
- **安全执行与质量验证：** 外部写操作统一走"草稿 → 权限校验 → 人工确认 → 审计"四段式，AI 不直接产生副作用；通过 SSE 推送工具调用与工作流进度，持久化 AgentRun / WorkflowRun / TaskRun 支持按 `run_id` 回放；建立 RAGAS 语义分与硬规则断言的双层评测，驱动 Prompt 与检索参数迭代。

**项目亮点**

- **五类分散信息收敛为一个工作台：** Issue、PR、Review、CI Job 与失败日志统一同步展示，研发周报从手工整理变为选定时间范围一键生成，支持单仓库与多仓库聚合。
- **专用 Agent 输出"可行动的结论"而非摘要：** Issue Agent 给出分类、优先级、复杂度与负责人建议；PR Review Agent 给出风险点、测试建议与合入结论；CI Debug Agent 定位失败根因、关联文件与排查步骤。
- **多 Agent 协同完成单轮问答覆盖不了的判断：** 以"这个 PR 能不能合"为例，Planner 拆分任务、按依赖调度、Observer 交叉检查证据缺失与结论冲突、Synthesis 汇总为统一建议，执行过程在前端实时可见。
- **AI 能力与风险边界同时设计：** 写操作三重闸门、全链路执行回放、双层评测，使"换模型或改 Prompt 后效果有没有退化"可量化、可回归。

## 5. 避免雷同：必须改的三处

16.2 明确警告过这一点。改完这三处，你的简历就和同学的不一样了。

### ① 换项目名

`DevFlow AI` 是课程统一名，一眼就认出来。

**首选 `Cairn`**，备选 `Docket` / `Signet`，保底 `RepoLens`。完整的候选表、撞名核查和"为什么叫这个"的说法见 **§9**。

要避开的：

- `RepoPilot` —— 已有一批同名项目，且 `-Pilot` / `-Copilot` 后缀现在很烂大街
- `CodePilot` 系列 —— 和 Copilot 撞
- `Quorum` / `Notary` / `Casefile` —— 都有知名同名项目，且会把面试官带偏到区块链 / 镜像签名 / 威胁情报

**技术栈里也把 `DevFlow` 相关的字样去掉**，否则改名没意义。

### ② 调职责顺序

按你要投的岗位排，不是按开发顺序排：

| 投什么 | 第一条放什么 |
|---|---|
| 后端 / 平台 | 研发数据底座（同步、隔离、幂等、32 张表） |
| AI 应用 / 算法 | RAG 与上下文工程（混合召回、父子块、Token 预算） |
| 全栈 | 全栈工作台（Next.js + SSE + 交互） |

### ③ 加一条"只有你有"的扩展

哪怕很小，只要是模板里没有的。从你项目里挑一个：

- **检索准入闸门**：检索结果先过 answer gate 判断"证据够不够"，不够就拒答而不是硬编（16.4 第 50/51 题正好考幻觉）
- **源码不走 RAG**：`code_file` 类型两边都不入（向量库和直查都不用），因为源码有精确结构，语义检索不如 grep，且频繁改动会让向量过期
- **目标解析不回退**：用户点名 Issue #42 但本地没同步时返回 422，绝不悄悄分析"最新那个"
- **工具白名单即沙箱**：Skill 激活后，调白名单外的工具会被强校验拦下

**这几条是真正能拉开差距的**，因为模板里没有，而且每条都能讲出"为什么这么设计"。

## 8. 面试开场三句话（配套用）

> 简历是钩子，这三句是让对方顺着钩子问。

1. **一句话定位**："这是一个把 GitHub 上的 Issue、PR、CI 和本地代码接进来，用 Agent 做第一轮分析的系统。"
2. **一句话差异**："和普通 Coding Agent 不同，它的重点是**基于证据回答**——答案要能指回具体的 Issue 或文件，而且 AI 不能直接改 GitHub。"
3. **一句话钩子**："我觉得最有意思的是上下文这块，怎么在有限 Token 里既保留最近对话、又不丢掉历史决策。"

第三句是故意的——它把面试官引到你已经讲得最透的地方（上下文工程），而不是让你被动等他挑。

## 9. 项目名候选（含撞名核查）

### 9.1 命名逻辑：从项目最独特的机制里取名，不要用通用词

`DevFlow` / `RepoPilot` / `CodeXxx` 这类名字的问题是：**它们描述的是品类，不是这个项目。** 面试官一天看 20 份简历，`-Pilot` 结尾的能见到 5 个。

你的项目有三个别人不容易复制的机制，名字应该从这里长出来：

| 机制 | 可用的隐喻 | 已排除（撞名） |
|---|---|---|
| 解决过的问题沉淀成记忆，下次直接复用 | 路标、石堆、卷宗、账本 | `Ledger`（硬件钱包）、`Scribe`（多个同名） |
| 每个 Issue/PR 像案子：凑证据 → 给结论 | 案卷、案情摘要、证物袋 | `Casefile`（澳洲威胁情报公司） |
| AI 只能起草，人签字才生效 | 印章、公证、会签 | `Notary`（CNCF 镜像签名项目）、`Quorum`（ConsenSys 区块链） |

### 9.2 推荐：三个有故事的

#### ① Cairn ｜引路石（首选）

- **读法**：/kern/，一个音节，好念
- **意象**：登山的人在岔路上堆石头，给后来的人指路
- **对应机制**：解决过的问题被确认后进入长期记忆 —— 每一个都是一块石头，堆起来给下一个遇到同样问题的人指路
- **简历呈现**：`Cairn（引路石）｜研发协作 Agent 平台`
- **被问"为什么叫这个"**：「Cairn 是山路上用石头堆的路标。这个项目也是把解决过的问题堆成路标——下一个人不用重新找路。」
- **撞名**：有一个同名独立游戏，领域完全无关；技术圈没有知名项目
- **风险**：面试官可能不认识这个词 —— 但这恰好给你一个 10 秒讲设计理念的机会，是加分不是减分

#### ② Docket ｜案卷

- **读法**：/ˈdɑːkɪt/，两个音节
- **意象**：法院的案卷表，每个案子有编号、证据、结论、裁决
- **对应机制**：Issue / PR 就是一份待审卷宗 —— 系统负责凑齐证据（检索 + 读代码），人负责签字；还有 audit log 留痕
- **简历呈现**：`Docket｜研发协作 Agent 平台`
- **被问"为什么叫这个"**：「Docket 是案卷。每个 Issue 和 PR 都是一份待审的卷宗，我做的事是让 Agent 把证据凑齐、给出建议，签字的人还是工程师。」
- **撞名**：低

#### ③ Signet ｜印鉴

- **读法**：/ˈsɪɡnɪt/，两个音节
- **意象**：印章戒指，盖上去才生效
- **对应机制**：整条 human-in-the-loop 设计 —— 草稿 → 权限校验 → 人工确认 → 审计，AI 不能自己盖章
- **简历呈现**：`Signet｜带人工确认闸门的研发协作 Agent`
- **被问"为什么叫这个"**：「Signet 是印章。这个项目所有改 GitHub 的动作都必须有人盖章，AI 只负责起草。」
- **撞名**：低
- **风险**：这个名字只覆盖"安全闸门"一个机制，如果你的简历主打 RAG / 上下文工程，会有点偏

### 9.3 保底：直白型（零解释成本）

| 名字 | 含义 | 适合场景 |
|---|---|---|
| **RepoLens** | 给仓库装一片透镜，看清里面发生了什么 | 投递量大、没时间解释名字时用 |
| **RepoBrief** | brief = 律师的案情摘要，正好是"证据 + 结论" | 想兼顾直白和一点专业感 |

直白型的优点是面试官一眼懂，缺点是记不住、也不体现设计思考。

| 名字 | 为什么不用 |
|---|---|
| Quorum | ConsenSys 的企业区块链平台，且 `quorum` 在分布式系统里是常用词，会被误认为是 Raft 类项目 |
| Notary | CNCF 的容器镜像签名项目，撞在"签名/审计"语义上 |
| Casefile | 澳洲一家威胁情报公司 |
| Loom | Atlassian 的录屏工具 |
| Arbiter | Dota 的装备名，偏游戏；且仲裁语义会让人以为是多 Agent 冲突裁决专用 |
| Ledger | 硬件钱包品牌 |
| Triage | 语义太窄，只覆盖 Issue 分诊 |

### 9.5 命名自查清单

投出去之前过一遍：

- [ ] 两个音节以内，面试官能一次念对（念不对的当场尴尬）
- [ ] 不用 `-GPT` / `-Copilot` / `-AI` / `-Pilot` 结尾
- [ ] 不用 `Dev` / `Code` 开头（`DevFlow` `DevOps` `CodeX` 全撞）

### 9.6 副标题模板

名字只是钩子，真正决定印象的是紧跟其后的那一行。公式：

> **[名字]｜[给谁] 的 [做什么] [形态]**

三个可直接用的：

```
Cairn（引路石）｜面向研发团队的 AI 协作 Agent 平台
Cairn｜把 GitHub 研发信息变成可核对结论的 Agent 系统
Cairn｜基于证据回答的研发协作 Agent
```

第二个最好——它一句话说清了"和普通 Copilot 的区别"（**可核对**），而这正是你项目最硬的差异点。

### 9.7 对标大厂简历风格：代号式命名（推荐用这一组）

> 参照两份高分简历的命名：`MindBridge`（实习平台）、`Thousand AI Moments`（黑客松项目）、
> `面向 Pull Request 研发治理的自进化 Multi-Agent Harness 系统`（项目标题）。
> 这种风格和你上面看到的 `Cairn` 不同：**不是文学词，而是"对象 + 机制隐喻"的产品化复合词。**

#### 构词法拆解

```
Mind + Bridge   = 心智 + 连接桥       → 把人的意图接到 AI 上
对象   机制隐喻
```

规律：**2~3 音节、PascalCase、无连字符、后半段是一个具体的"器械"隐喻**（Bridge / Gate / Lens / Prism / Loom）。
好处是面试官听一遍就记住，而且名字本身能当"设计理念"讲。

#### 候选（已做撞名核查）

| 代号 | 构词 | 意象 | 对应项目机制 | 撞名 |
|---|---|---|---|---|
| **MergeGate** | Merge + Gate | 合入闸门：过得了才放行 | PR 合入判断 + 人工确认闸门（双关） | ✅ 未发现同名项目 |
| **RepoPrism** | Repo + Prism | 棱镜：一束混杂光 → 分离成光谱 | 散在 Issue/PR/CI/代码的信息 → 结构化可核对结论 | ⚠️ `Prism` 有同名 WPF 框架，领域无关 |
| **TraceWeave** | Trace + Weave | 把散点轨迹织成一条线 | AgentRun / WorkflowRun / TaskRun 回放 | ✅ 未发现 |
| **DevDocket** | Dev + Docket | 案卷 | 证据 + 待审 + 签字 + 留痕 | ✅ 未发现 |
| ~~ContextLoom~~ | Context + Loom | 织机 | 上下文分层组装 | ❌ **已有一个同功能 MCP 项目叫 Context Loom**（把聊天请求+本地项目压成带引用的 prompt），撞得最狠 |
| ~~RepoLattice~~ | Repo + Lattice | 晶格 | 代码图谱 | ❌ 已有 `ContextLattice`，同赛道（memory/context orchestrator） |
| ~~RepoBridge~~ | Repo + Bridge | 桥 | — | ❌ 直接照搬 MindBridge 的构词，一眼看出是抄 |

#### 首选：MergeGate

**理由**：

1. **名字就是你的旗舰场景。** 你的文档里反复出现的那句"这个 PR 能不能合"，就是 gate 的语义。
2. **双关。** 一层是 Git 的 merge gate（合入闸门），一层是 human-in-the-loop 的审批闸门 —— 正好覆盖你项目最硬的两个设计。
3. **两个音节，好念好记。** 面试官听一遍就能复述。
4. **未撞名。** 搜不到同名项目。

**代价**：名字偏"PR 场景"，比整个系统窄。但这正是截图里那位候选人的做法 ——
系统叫 Multi-Agent Harness，简历标题却写"面向 Pull Request 研发治理"。**用最锋利的场景做钩子，用定位句覆盖全景。**

#### 简历标题写法（照截图的句式）

```
[MergeGate]｜面向 PR 合入决策的证据化 Multi-Agent 评审系统
```

同款可替换：

```
RepoPrism｜面向研发信息收敛的多 Agent 分析与问答平台
TraceWeave｜面向长对话 Agent 的上下文工程与可观测系统
DevDocket｜面向研发协作的证据化 Multi-Agent 工作台
```

句式模板：**`[代号]｜面向 [具体场景] 的 [技术特性] [形态]`**

- `面向 …` = 场景，越具体越好（不要写"面向研发团队"）
- `[技术特性]` = 你区别于普通方案的那一点（证据化 / 自进化 / 可核对）
- `[形态]` = Multi-Agent 系统 / 平台 / 工作台 / 引擎

#### 一个额外的注意点：开源就要更在意撞名

截图里那位把项目标了「开源项目」并附 GitHub 链接。如果你也打算开源：

- 名字要在 GitHub 上搜不到同名的活跃仓库
- 仓库名建议 `mergegate`（全小写），别用 `MergeGate-AI`
- 开源后这个名字会长期跟着你，比简历上的临时用名更需要谨慎
