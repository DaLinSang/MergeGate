# 6.4 GitHub 同步链路 · 重新组织版

> 对飞书文档《6.4｜源码解析：GitHub 协作数据怎样同步到系统》的重新梳理
> 原文 909 行 / 2.6 万字，本文按「分层 → 数据流 → 设计意图」重排，并标注了原文与项目实际代码的差异

---

## 阅读前：先定位这一节在讲什么

**一句话**：GitHub 上的 Issue / PR / CI 是外部数据，系统要**定时把它们搬进本地 PostgreSQL**，之后所有查询都读本地，不再实时打 GitHub。

**它解决的问题**：

| 如果不做同步会怎样 | 做了同步之后 |
|---|---|
| 每次打开页面都调 GitHub API，慢 | 本地查询，毫秒级 |
| GitHub 免费额度 60 次/小时（无 token） | 只同步时不限量，读取不限 |
| GitHub 挂了页面就白屏 | GitHub 挂了照样能看昨天的快照 |
| 没法做跨对象分析（比如"这个 PR 关联哪些 Issue"） | 数据都在本地，随便 JOIN |

**这一节的范围**：只管"搬数据 + 读数据"。RAG 索引、向量检索、Agent 调用都是**下一节**的事。

## 一、为什么原文档读起来乱（4 个原因）

理解这一点，你就知道该怎么读了。

### 原因 1：按"写代码的顺序"讲，不是按"数据流动的顺序"讲

原文的章节顺序是：

```
models.py → client.py → issues.py → schemas → repos_sync.py → routes
```

这是**作者当初敲代码的顺序**（先建表、再写 HTTP 客户端、再写一个资源、再串起来、最后挂路由）。

但**运行时数据的顺序**是反过来的：

```
routes → repos_sync → github/ → models
```

所以读原文时，你会不断产生"我为什么要先看这个文件"的疑惑——因为你被要求先看"终点"再看"起点"。

### 原因 2：从不点明"这是第几层"

原文混着讲四个不同层的东西，但从不标注：

| 原文讲的代码 | 实际属于哪一层 |
|---|---|
| `models.py` | 数据层 |
| `client.py` / `issues.py` | 外部适配层 |
| `repos_sync.py` | 业务层（同步核心） |
| `repos.py` / `webhooks.py` | 路由层 |

没有"层"的框架，所有文件在你脑子里就是平铺的一堆，自然觉得乱。

### 原因 3：标题全是问句，缺少"我们现在在哪"的定位

"GitHub 对象是怎样进入内部模型的？"——这是个好问题，但它没告诉你：
- 这是 5 步里的第几步？
- 前面已经完成了什么？
- 后面还剩什么？

读完一节，你不知道自己走到了哪。

### 原因 4：代码是教学简化版，与项目实际代码有 6 处出入

你对照源码时会发现对不上，越看越困惑。详见第五节。

## 二、五层结构（这才是骨架）

```
┌──────────────────────────────────────────────────────┐
│ 第 1 层 · 触发                                        │
│   连接仓库 / 手动刷新 / 定时任务 / Webhook              │
│   → 四个入口，一个同步核心                             │
└────────────────────┬─────────────────────────────────┘
                     ▼
┌──────────────────────────────────────────────────────┐
│ 第 2 层 · 路由   api/routes/                          │
│   repos.py    → connect / sync / sync-status / 读取   │
│   webhooks.py → 验签 + 安排后台同步                    │
│   职责：接参数、查仓库是否存在、转交业务层              │
└────────────────────┬─────────────────────────────────┘
                     ▼
┌──────────────────────────────────────────────────────┐
│ 第 3 层 · 同步核心   services/repos_sync.py            │
│   sync_repository()        ← 唯一的数据写入规则        │
│   sync_repository_by_id()  ← 给后台任务用的包装        │
│   职责：拉取 → 映射 → 落库 → 更新 last_sync_at        │
└────────────────────┬─────────────────────────────────┘
                     ▼
┌──────────────────────────────────────────────────────┐
│ 第 4 层 · 外部适配   services/github/                 │
│   client.py        → 统一 HTTP + Header + 认证        │
│   issues.py        → /issues                          │
│   pull_requests.py → /pulls, /files, /comments        │
│   actions.py       → /runs, /jobs, /logs              │
│   职责：只负责"取回来"，不决定存哪张表                  │
└────────────────────┬─────────────────────────────────┘
                     ▼
┌───────────────────────┬──────────────────────────────┐
│ GitHub REST API       │ PostgreSQL                    │
│ （读外部事实）         │ （写本地快照）                 │
└───────────────────────┴──────────────────────────────┘
```

**记住这个依赖方向**：上层调下层，下层不知道上层的存在。
- `client.py` 不知道有 `sync_repository`
- `repos_sync.py` 不知道有 HTTP 路由
- `models.py` 不知道任何业务逻辑

这就是"分层"的意义：**改一层不会震塌另一层**。

## 三、按数据流重讲：5 个步骤

### Step 1 · 触发：四个入口，一个核心

| 入口 | 谁触发 | 走哪条路 |
|---|---|---|
| **连接仓库** | 用户在 `/repos` 页面填表 | `POST /api/repos/connect` |
| **手动刷新** | 用户点"同步"按钮 | `POST /api/repos/{id}/sync` |
| **定时任务** | 后端每 300 秒自动跑 | `scheduler.py` 的循环 |
| **Webhook** | GitHub 有事件时主动推 | `POST /api/webhooks/github` |

**关键设计**：四个入口最终都调**同一个** `sync_repository()`。

```
连接仓库 ──┐
手动刷新 ──┤
定时任务 ──┼──> sync_repository()  ← 规则只写一份
Webhook ───┘
```

**为什么重要**：如果每个入口各写一套同步逻辑，改一个字段映射就要改四处，必然漏改。

### Step 2 · 拉取：三个资源函数

`services/github/` 下每个函数只干一件事——**调一个 GitHub 接口，返回原始 JSON**。

| 函数 | 请求的 GitHub 接口 |
|---|---|
| `list_issues()` | `GET /repos/{owner}/{repo}/issues` |
| `list_pull_requests()` | `GET /repos/{owner}/{repo}/pulls` |
| `list_pull_request_files()` | `GET /repos/{owner}/{repo}/pulls/{n}/files` |
| `list_pull_request_review_comments()` | `GET /repos/{owner}/{repo}/pulls/{n}/comments` |
| `list_workflow_runs()` | `GET /repos/{owner}/{repo}/actions/runs` |
| `list_workflow_run_jobs()` | `GET /repos/{owner}/{repo}/actions/runs/{id}/jobs` |
| `get_workflow_run_logs()` | `GET /repos/{owner}/{repo}/actions/runs/{id}/logs`（zip，要解压） |

**两个容易忽略的细节**：

**① Issue 接口会混进 PR，必须过滤**

```python
items = await client.get(f"/repos/{owner}/{repo}/issues", {"state": "all", "per_page": limit})
return [item for item in items if "pull_request" not in item]
```

GitHub 的 `/issues` 接口会把 PR 也当成 Issue 返回。判断依据：**带 `pull_request` 字段的就是 PR**。不过滤会导致 PR 被重复存两遍。

**② 必须用 `state=all` 而不是 `state=open`**

```python
{"state": "all", ...}
```

如果只拉 open 的，Issue 被关闭后本地还是 `open`——**状态永远更新不了**。

### Step 3 · 映射：外部 JSON → 内部模型

这是整条链路**最需要动脑**的部分。

GitHub 返回的 JSON 长这样（简化）：

```json
{
  "id": 1234567890,
  "number": 42,
  "title": "登录接口报 500",
  "state": "open",
  "labels": [{"name": "bug"}, {"name": "P1"}],
  "user": {"login": "alice"},
  "assignees": [{"login": "bob"}]
}
```

要映射成内部模型：

| GitHub 字段 | 内部字段 | 注意点 |
|---|---|---|
| `id` | `github_issue_id` | **用于判断"是不是同一个对象"** |
| `number` | `number` | 用户看到的 `#42` |
| `title` | `title` | |
| `state` | `state` | |
| `labels[].name` | `labels` | **嵌套结构要拍平**成 `["bug","P1"]` |
| `user.login` | `author` | 嵌套取一层 |
| `assignees[].login` | `assignees` | 列表拍平 |
| `updated_at` | `updated_at` | ISO 8601 字符串要转 datetime |

**时间转换的坑**：

```python
def parse_github_datetime(value: str | None) -> datetime | None:
    if not value:
        return None
    return datetime.fromisoformat(value.replace("Z", "+00:00"))
```

GitHub 返回 `"2026-10-18T05:30:00Z"`，Python 的 `fromisoformat` 不认 `Z` 结尾，必须替换成 `+00:00`。

### Step 4 · 落库：核心是"存在就更新，不存在才插入"

```python
issue = (
    db.query(Issue)
    .filter(
        Issue.repo_id == repo.id,              # ← 必须锁仓库
        Issue.github_issue_id == item.get("id"),  # ← 必须锁对象
    )
    .one_or_none()
)
if issue is None:
    issue = Issue(repo_id=repo.id, github_issue_id=item.get("id"), ...)
    db.add(issue)

issue.title = item.get("title") or issue.title   # 存在 → 覆盖字段
```

**两个条件缺一不可**：

| 只写 `github_issue_id` | 只写 `repo_id` | 两个都写 |
|---|---|---|
| 两个仓库都有 Issue #42 → 拿错项目 | 返回该仓库所有 Issue → 无法定位单条 | ✅ 正确 |

这就是原文强调的"**仓库串线**"问题。

**三类资源的落库规则不一样**：

| 资源 | 规则 | 为什么 |
|---|---|---|
| Issue | **逐条 upsert**（按 `repo_id + github_issue_id`） | 数量少，逐条更新精确 |
| PR 本体 | 逐条 upsert | 同上 |
| **PR 的 files / comments** | **整组删除再插入** | 子资源可能被删（比如 rebase 后文件变了），增量更新无法感知"消失" |
| Workflow Run | 逐条 upsert | |
| Run 的 jobs | 整体覆盖 JSON 字段 | jobs 是嵌套结构，用 JSON 存 |
| Run 的日志 | 仅 `conclusion == "failure"` 时拉取 | 省流量、省存储 |

**整组替换的代码**：

```python
db.query(PRFile).filter(PRFile.pr_id == pr.id).delete()   # 先全删
files = await list_pull_request_files(...)                 # 再全拉
for item in files:
    db.add(PRFile(pr_id=pr.id, filename=item.get("filename") or "", ...))
```

**代价**：如果这次拉取失败（网络问题），`files` 是空列表，就把原来的数据删光了——**留下一个空快照**。这是原文自己承认的缺陷。

### Step 5 · 读取：永远不碰 GitHub

```python
@router.get("/repos/{repo_id}/issues")
async def list_issues(repo_id: UUID, db: Session = Depends(get_db)):
    return (
        db.query(Issue)
        .filter(Issue.repo_id == repo_id)     # 只按仓库过滤
        .order_by(Issue.number.desc())
        .all()
    )
```

**关键点**：这些读取接口**完全不 import `GitHubClient`**。

```
写入路径：触发 → GitHub API → sync_repository → PostgreSQL
读取路径：页面 → 路由 → PostgreSQL（到此为止）
```

**为什么这样设计**：
- GitHub 挂了不影响读
- 读取速度从"网络往返 500ms"变成"本地查询 5ms"
- 不消耗 GitHub 的 API 额度

## 四、三个必须分清的概念

### 4.1 三个 ID，各管一件事

| ID | 是什么 | 用在哪 |
|---|---|---|
| `Repository.id` | 系统自己生成的 UUID | **所有表的 `repo_id` 外键** |
| `Issue.repo_id` | 这条 Issue 属于哪个仓库 | 查询时**必须带上的过滤条件** |
| `Issue.github_issue_id` | GitHub 侧的原始 ID | **判断"下次拉到的是不是同一个对象"** |

**为什么不用 GitHub ID 当主键**：
- GitHub ID 是别人的，万一将来接入 GitLab，ID 体系就冲突了
- 用内部 UUID 可以支持多 provider（`repositories.provider` 字段就是这个用途）

**`number` 和 `github_issue_id` 的区别**：
- `number` = 用户看到的 `#42`，**会变**（仓库迁移时可能重新编号）
- `github_issue_id` = 内部唯一 ID，**永不变** → 所以用它做匹配

### 4.2 同步路径 vs 读取路径

这是原文最核心的洞察，但藏在很后面：

```
【同步路径】写
连接/刷新/定时/Webhook → GitHub API → sync_repository → PostgreSQL

【读取路径】读
页面/工具/Agent → 路由 → PostgreSQL（不碰 GitHub）
```

**两条路径唯一的数据交集是 PostgreSQL**。理解了这一点，你就理解了整个架构。

### 4.3 增量更新 vs 整组替换

| 策略 | 用在哪 | 优点 | 缺点 |
|---|---|---|---|
| 增量更新（upsert） | Issue、PR 本体、Run | 精确，不丢数据 | 感知不到"删除" |
| 整组替换（delete + insert） | PR files、comments | 能清除旧数据 | 失败时留下空快照 |

**判断标准**：子资源会被"整体替换"吗？会 → 用整组替换；只是"逐条变化"吗？→ 用增量。

## 五、文档与项目实际代码的 6 处差异

**这是你对照源码时最容易困惑的地方**。原文的代码是"教学简化版"，项目实际代码已经演进了。

### 差异 1：`RepoConnectRequest` 的字段

**原文**：

```python
class RepoConnectRequest(BaseModel):
    owner: str          # ← 必填
    repo: str           # ← 必填
    initial_sync_limit: int = Field(default=5, ge=1, le=50)
    sync_issues: bool = True
    sync_pull_requests: bool = True
    sync_workflow_runs: bool = True
```

**实际**（`backend/app/schemas/repos.py`）：

```python
class RepoConnectRequest(BaseModel):
    owner: str | None = None        # ← 可选
    repo: str | None = None         # ← 可选
    token: str | None = None
    github_token: str | None = None
    provider: str = "github"
    api_base_url: str | None = None
    local_path: str | None = None   # ← 文档没提
    clone_parent_dir: str | None = None  # ← 文档没提

    initial_sync_limit: int = Field(default=5, ge=1, le=50)

```

**为什么 `owner`/`repo` 变成可选**：因为支持另外两种接入方式（见差异 2）。

### 差异 2：实际支持 3 种接入方式，文档只讲了 1 种

| 方式 | 传什么 | 行为 |
|---|---|---|
| ① 远程接入 | `owner` + `repo` | 调 GitHub API 验证仓库存在 |
| ② 本地路径 | `local_path` | 读该目录的 `.git/config`，**自动推断** owner/repo，`checkout_mode="local"` |
| ③ 克隆到指定目录 | `clone_parent_dir` | 计算克隆目标路径 |

**方式 ② 的实现**（`repos.py`）：

```python
def _inspect_local_repository(raw_path: str) -> tuple[Path, GitRemoteInfo]:
    # 读 .git/config 里的 remote url，解析出 owner/repo
```

**这个能力很重要**：意味着你可以直接接入本地已有的项目，不用先传到 GitHub。

### 差异 3：`GitHubClient` 不只是"读"

**原文说**："`GitHubClient` 只负责发送 HTTP 请求并解析响应。"

**实际**：它还有写操作。

```python
class GitHubClient:
    # 读
    async def get(...)           # 原文有
    async def get_bytes(...)     # 文档没有（下载 CI 日志 zip 用）
    async def get_repo(...)      # 原文有

    # 写 ← 文档完全没提
    async def post(...)
    async def patch(...)
    async def create_issue(...)
    async def close_issue(...)
    async def add_issue_labels(...)
    async def create_issue_comment(...)
```

**这些写操作服务于谁**：`ActionDraft` 的确认执行。AI 生成草稿 → 人工确认 → 调这些方法真正改 GitHub。

所以原文那句话应该改成："`GitHubClient` 只负责和 GitHub 通信，不决定业务规则。"

### 差异 4：token 的优先级

**原文**：

```python
token = settings.github_token      # 只用全局
```

**实际**：

```python
token = decrypt_token(repo.github_token_encrypted, settings.token_encryption_key) \
        if repo.github_token_encrypted else None
```

**逻辑**：**仓库级 token 优先**，没有才回退到全局 `GITHUB_TOKEN`。

**为什么**：不同仓库可能属于不同账号/组织，需要不同权限。仓库级 token 加密存在 `repositories.github_token_encrypted` 字段里。

### 差异 5：连接后还有后台任务

**原文**：连接完返回结果就结束了。

**实际**：

```python
background_tasks.add_task(sync_repository_code_analysis_by_id, repo.id)
```

连接成功后还会**异步建代码图谱**（解析代码符号、调用关系）。这是文档没提的后续动作。

### 差异 6：路由注册带 tags

**原文**：

```python
app.include_router(repos.router, prefix="/api/repos")
```

**实际**：

```python
app.include_router(repos.router, prefix="/api/repos", tags=["repos"])
```

**影响**：`tags` 决定了 `/docs` 页面上接口的分组显示。不影响功能，但影响可读性。

## 六、为什么这样设计（5 个关键决策）

### 决策 1：为什么要落库，而不是每次实时查 GitHub

| 维度 | 实时查 | 落库 |
|---|---|---|
| 响应速度 | 每次 200-800ms | 5-20ms |
| API 额度 | 无 token 60 次/小时 | 只同步时消耗 |
| 离线可用 | ❌ | ✅ |
| 跨对象分析 | 做不到 | 可以 SQL JOIN |

**结论**：这是"用存储换速度"的经典取舍。数据同步是所有数据密集型系统的第一步。

### 决策 2：为什么用内部 UUID 而不是 GitHub ID 做主键

```python
id: Mapped[uuid.UUID] = mapped_column(Uuid(as_uuid=True), primary_key=True, default=uuid.uuid4)
github_issue_id: Mapped[int | None] = mapped_column(BigInteger, nullable=True)
```

**原因**：
- **解耦**：内部主键由自己掌控，不受外部系统影响
- **多 provider**：`repositories.provider` 字段预留了接入 GitLab / Gitee 的能力
- **安全**：不暴露外部 ID 的规律

代价：多一个字段要维护（`github_issue_id` 专门用来做同步匹配）。

### 决策 3：为什么子资源用"整组替换"

因为**无法感知删除**。

假设 PR 原来改了 5 个文件，rebase 后只改 3 个。如果用增量更新：
- 你只能看到"这 3 个文件有变化"
- 那 2 个被移除的文件**还留在数据库里**

整组替换最彻底：先删光，再按最新结果插入。

**代价**：拉取失败时得到空快照。原文自己指出了这个缺陷，正确做法应该是：
1. 先拉取到内存
2. 拉取成功才删旧数据
3. 在同一个事务里完成

### 决策 4：为什么 Webhook 不直接用 payload 改库

GitHub 的 Webhook payload 里**已经有**变更后的对象数据，理论上可以直接解析入库，省一次 API 调用。

但项目选择：**拿到事件后，重新调一次完整同步**。

```python
background_tasks.add_task(sync_repository_by_id, repo.id, RepoSyncRequest(limit=...))
```

**原因**：避免维护两套映射逻辑。

| 方案 | 要维护什么 |
|---|---|
| 直接用 payload | 完整同步映射 + 每种事件的增量映射（issues / pull_request / workflow_run / push / check_suite / check_run 各一套） |
| 重新完整同步 | 只有一套 |

**代价**：多一次 GitHub API 请求。
**收益**：代码量减少一半以上，且不会出现"增量映射漏字段"的 bug。

### 决策 5：为什么定时任务要先关 Session

```python
db = SessionLocal()
try:
    repos = db.query(Repository).filter(...).all()
    repo_ids = [repo.id for repo in repos]     # 只取 ID
finally:
    db.close()                                  # 立刻关闭

for repo_id in repo_ids:
    await sync_repository_by_id(repo_id, ...)   # 每个仓库用自己的 Session
```

**为什么**：如果拿着一个 Session 遍历所有仓库同步：
- 同步可能耗时几分钟，**长事务会锁表**
- 一个仓库失败会污染整个 Session 状态

**正确做法**：先只查 ID，关掉 Session，再逐个仓库开新 Session。

### 三个易错点

1. **Issue 接口会返回 PR** → 必须按 `"pull_request" not in item` 过滤
2. **必须用 `state=all`** → 否则关闭状态永远同步不过来
3. **查询必须带 `repo_id`** → 否则两个仓库的 #42 会串线

### 原文的一句话总结（值得记住）

> **入口可以增加，同步规则必须收口。**

四个触发入口，一个 `sync_repository()`。这是整个设计的灵魂。
