# 第 0 章 先读这一页（5 分钟建立全局印象）

## 0.1 这个项目是干什么的

**DevFlow AI 是一个"懂你 GitHub 仓库的 AI 助手"。**

你在 GitHub 上维护一个代码仓库，日常会遇到这些问题：

| 你的痛点                   | DevFlow AI 能做什么            |
| ---------------------- | -------------------------- |
| 来了 20 个 Issue，不知道先处理哪个 | 分析 Issue 的分类、优先级、复杂度、该派给谁  |
| 同事提了个 500 行的 PR，看不出风险  | 审查 PR diff，指出风险点、阻塞项、测试建议  |
| CI 突然红了，日志几千行找不到原因     | 分析失败日志，给出失败类型和排查步骤         |
| 想查"这个项目的鉴权是怎么设计的"      | 语义检索项目文档/Issue/PR，给出带引用的回答 |
| 想知道这周团队干了什么            | 自动生成研发周报                   |

它的本质是一个**带工具的对话式 Agent**：你用自然语言提问，它自己去查数据库、读代码、搜文档，然后回答你。

## 0.2 三个必须记住的核心概念

整个项目就围绕这三件事展开，看懂这三个，就看懂了 70%：

### 概念一：数据同步（把 GitHub 搬进本地）

GitHub 上的 Issue、PR、CI 日志不在你本地。所以系统第一步是**用 GitHub API 把它们抓下来，存进自己的 PostgreSQL 数据库**。

> 关键文件：`backend/app/services/repos_sync.py`

### 概念二：Agent + 工具调用（AI 自己动手查）

大模型（DeepSeek）本身**看不到**你的数据库和代码。所以系统给了它 14 个"工具"：

```
workspace.read_file       → 读本地代码文件
rag.search_similar_documents → 搜知识库
issue_agent.analyze_issue → 分析某个 Issue
...
```

大模型在思考过程中会**自己决定调用哪个工具**，拿到结果再继续想，直到能回答为止。这个"想 → 调工具 → 看结果 → 再想"的循环，就是 Agent 的本质。

> 关键文件：`backend/app/services/agents/chat_agent.py`（2066 行，全项目最核心）

### 概念三：RAG（检索增强生成）

大模型不知道你项目内部的知识。RAG 的做法是：**先把文档切碎、变成向量存起来；用户提问时，先检索出最相关的几段，再连同问题一起喂给大模型**。

```
文档 → 切片 → 向量化 → 存 Milvus（向量库）
问题 → 向量化 → 相似度检索 → 取出相关段落 → 拼进 Prompt → LLM 回答
```

> 关键目录：`backend/app/services/rag/`（12 个文件）

# 第 2 章 读懂这个项目所需的 Python 语法

> 这一章是为你"不熟悉 Python"专门写的。每个语法点都配了**本项目真实代码**，看完就能读懂项目里 90% 的代码。

## 2.1 类型注解：`name: str` 是什么意思

Python 是动态语言，但现代 Python 会**标注类型**（给人和 IDE 看的，运行时不强制检查）。

```python
def encrypt_token(token: str, secret: str) -> str:
    ...
```

读法：

- `token: str` → 参数 token 应该是字符串
- `-> str` → 这个函数返回字符串

再看复杂一点的（`app/core/config.py`）：

```python
llm_api_key: str | None = None
```

读法：`str | None` 表示"字符串 **或** 空值"，`= None` 是默认值。等价于其他语言里的 `Optional[str]`。

**为什么项目里到处都写类型？**

1. IDE 能自动补全、跳转、报错
2. Pydantic 靠类型做运行时校验（见 2.9）
3. 相当于"自带文档"，不用看实现就知道参数是什么

## 2.2 类、`self`、`__init__`

```python
class LLMClient:
    def __init__(self) -> None:
        self.base_url = settings.llm_base_url.rstrip("/")
        self.api_key = settings.llm_api_key
        self.model = settings.llm_model
```

- `class LLMClient:` → 定义一个类（模板）
- `__init__` → 构造函数，创建对象时自动执行
- `self` → 指"这个对象自己"，相当于其他语言的 `this`。**Python 必须显式写出来**
- `self.base_url = ...` → 给这个对象挂一个属性

使用：

```python
client = LLMClient()        # 触发 __init__，三个属性被赋值
print(client.model)         # 读属性
```

## 2.3 继承：`class User(Base)`

```python
class User(Base):
    __tablename__ = "users"
    id: Mapped[uuid.UUID] = mapped_column(Uuid(as_uuid=True), primary_key=True)
```

- `class User(Base)` → User 继承自 Base
- `Base` 在 `app/db/session.py` 里定义：`class Base(DeclarativeBase): pass`
- SQLAlchemy 通过这个继承关系**自动知道 User 对应数据库里的一张表**

`pass` 的意思是"什么都不做"，只是一个占位符（Python 语法要求类体不能为空）。

## 2.4 异步：`async def` / `await`

这个项目大量使用异步，因为要同时等很多网络请求（GitHub API、LLM API、数据库）。

```python
async def chat_text(self, system_prompt: str, user_message: str) -> str:
    async with httpx.AsyncClient(timeout=60) as client:
        response = await client.post(...)
        return str(...)
```

读法：

- `async def` → 定义一个"协程函数"，调用它不会立刻执行，而是返回一个协程对象
- `await` → "在这里等一下，让出 CPU 去干别的"
- **关键规则**：`await` 只能出现在 `async def` 里面

**为什么用异步？** 假设要同时调 5 个 API，同步写法要串行等 5 次；异步写法可以同时发出去，总耗时接近最慢的那一个。

**实际影响**：你看到 `async def` 就知道"这个函数需要 `await` 才能调用"。

## 2.5 装饰器：`@` 开头的行

装饰器 = "给函数套一层外壳，改变它的行为"。项目里到处都是：

```python
@app.get("/health")
async def health() -> dict[str, str]:
    return {"status": "ok"}
```

`@app.get("/health")` 的意思是：**把这个函数注册成 HTTP GET /health 的处理器**。你不用手动调用它，浏览器访问时 FastAPI 会自动调。

项目里的其他装饰器：

| 装饰器                     | 位置                           | 作用              |
| ----------------------- | ---------------------------- | --------------- |
| `@app.get/post`         | `api/routes/*.py`            | 注册 HTTP 接口      |
| `@lru_cache(maxsize=4)` | `services/rag/embeddings.py` | 缓存函数结果（模型只加载一次） |
| `@property`             | 各处                           | 把方法伪装成属性        |
| `@dataclass`            | `chat_memory.py`             | 自动生成构造函数        |

## 2.6 数据类：`@dataclass`

```python
@dataclass
class AssembledContext:
    system_context: str
    history_messages: list[dict[str, str]]
    evidence: list[dict[str, Any]]
    compression_stats: dict[str, Any] = field(default_factory=dict)
```

`@dataclass` 会自动帮你生成 `__init__`，所以你不用写：

```python
def __init__(self, system_context, history_messages, evidence, ...):
    self.system_context = system_context
    ...
```

它的定位是"**只装数据、不带行为的容器**"。项目里所有 `AssembledContext`、`ContextBudget` 这类都是它。

## 2.7 `yield`：生成器

```python
def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()
    try:
        yield db          # ← 关键
    finally:
        db.close()
```

`yield` 和 `return` 的区别：

- `return` 一次返回，函数结束
- `yield` **暂停**函数，把值交出去；下次需要时从暂停处继续

这段代码的实际效果是：FastAPI 每个请求进来先创建数据库连接（`yield db` 交出去），请求处理完后回来执行 `finally` 关闭连接。**这是"自动开关资源"的经典写法。**

## 2.8 推导式：一行写循环

```python
def _cors_origins() -> list[str]:
    return [origin.strip() for origin in settings.cors_origins.split(",") if origin.strip()]
```

等价于：

```python
result = []
for origin in settings.cors_origins.split(","):
    if origin.strip():
        result.append(origin.strip())
return result
```

看到 `[表达式 for 变量 in 可迭代对象 if 条件]` 就是这个模式。

还有字典推导式：

```python
tool_map = {name: func for name, func in tools.items()}
```

## 2.9 Pydantic：用类做数据校验

项目里 `app/schemas/` 下 19 个文件全是这个：

```python
class RepoSyncRequest(BaseModel):
    sync_issues: bool = True
    sync_pull_requests: bool = True
    sync_workflow_runs: bool = True
    limit: int = 50
```

`BaseModel` 来自 Pydantic。它的魔法是：**前端传来的 JSON 会自动变成这个类的实例，类型不对会直接报错 422**。

```python
payload = RepoSyncRequest(**json_data)   # 自动校验
payload.limit                            # 已保证是 int
```

这就是为什么路由函数可以直接写 `payload: RepoSyncRequest` —— FastAPI 会帮你完成"JSON → 对象 + 校验"。

## 2.10 `dict`、`Any`、`.get()`

```python
def login_of(user: dict | None) -> str | None:
    return user.get("login") if user else None
```

- `dict` → 字典，`{"key": "value"}`
- `.get("login")` → 取 key，**不存在时返回 None 而不是报错**（用 `user["login"]` 则会 KeyError）
- `Any` → 任意类型（通常用在 JSON 这种结构不固定的地方）


## 2.11 `with`：上下文管理器

```python
with httpx.AsyncClient(timeout=60) as client:
    response = await client.post(...)
```

`with` 保证**离开代码块时自动清理资源**（关闭连接、关闭文件）。等价于 try/finally。

## 2.12 f-string：字符串插值

```python
raise HTTPException(status_code=403, detail=f"需要权限：{permission}")
```

`f"..."` 里的 `{变量}` 会被替换成变量的值。

## 2.13 抽象基类：`ABC`

```python
class BaseAgent(ABC):
    name: str
    description: str

    @abstractmethod
    async def run(self, input_data: dict, context: dict) -> dict:
        ...
```

`ABC` = Abstract Base Class（抽象基类）。它定义"**所有 Agent 必须长这样**"：

- 必须有 `name`、`description` 属性
- 必须实现 `run()` 方法

继承它的类如果没实现 `run()`，实例化时会直接报错。**这是一种"强制契约"**——保证 13 个 Agent 的调用方式完全一致。

## 2.14 `import` 的三种写法

```python
import uuid                              # 导入整个模块，用 uuid.uuid4()
from datetime import datetime            # 从模块导入具体名字
from app.db.models import Base, User     # 从自己的包导入
```

`app.` 开头的 import 能生效，是因为启动时工作目录在 `backend/`（这也是为什么 PyCharm 的运行配置里 Working directory 必须设成 `backend/`）。

## 2.15 `if __name__ == "__main__"`

```python
if __name__ == "__main__":
    main()
```

意思是"**只有直接运行这个文件时才执行**，被别的文件 import 时不执行"。项目里用得不多，但在脚本里常见。

## 2.16 小结：看到这些词你就知道在干什么

| 代码形态                      | 含义               |
| ------------------------- | ---------------- |
| `def foo(x: int) -> str:` | 普通函数             |
| `async def foo():`        | 异步函数，调用要 `await` |
| `@app.get("/path")`       | 注册 HTTP 接口       |
| `class Foo(Base):`        | 继承，通常是数据库表       |
| `yield`                   | 生成器，用于资源管理       |
| `[x for x in y]`          | 列表推导             |
| `x.get("k")`              | 安全取字典值           |
| `f"{x}"`                  | 字符串插值            |
| `x \| None`               | 可能是空值            |
| `@dataclass`              | 纯数据容器            |
| `ABC` + `@abstractmethod` | 强制子类实现的契约        |

# 第 3 章 后端分层架构

## 3.1 五层结构

后端严格分成五层，**依赖方向永远是单向的**（上层可以调下层，下层不能调上层）：

```
┌─────────────────────────────────────────────┐
│  ① 路由层  api/routes/                       │  接 HTTP 请求，做参数校验，返回响应
│     18 个文件，如 chat.py / repos.py          │
└───────────────────┬─────────────────────────┘
                    │ 调用
┌───────────────────▼─────────────────────────┐
│  ② 业务层  services/                         │  真正的业务逻辑
│     agents/ rag/ evals/ github/ llm/ ...     │
└───────────────────┬─────────────────────────┘
                    │ 调用
┌───────────────────▼─────────────────────────┐
│  ③ 数据层  db/                               │  数据库连接 + 表模型

  ⑥ 契约层 schemas/ ← 路由层用它定义输入输出格式
```

## 3.2 每一层的职责边界

| 层   | 目录            | 该做什么                        | **不该做什么**                |
| --- | ------------- | --------------------------- | ------------------------ |
| 路由层 | `api/routes/` | 解析请求、校验参数、调 service、返回 JSON | ❌ 不写复杂业务逻辑、不直接写 SQL      |
| 业务层 | `services/`   | 全部业务规则、算法、外部调用              | ❌ 不处理 HTTP、不关心 JSON 长什么样 |
| 数据层 | `db/`         | 表结构定义、连接管理                  | ❌ 不含业务判断                 |
| 契约层 | `schemas/`    | 定义请求/响应的字段与类型               | ❌ 不含逻辑                   |
| 配置层 | `core/`       | 读环境变量、加密、日志                 | ❌ 不含业务                   |

## 3.3 为什么要这样分层

这是本项目最重要的工程决策，理解了它，你就理解了"为什么代码要这样组织"。

**问题**：如果所有代码都写在一个文件里，会怎样？

**答案**：三个致命问题——

1. **改一处坏一片**：改数据库字段，所有 SQL 都要跟着改
2. **没法测试**：想测"Issue 分类算法"，必须启动整个 HTTP 服务
3. **没法复用**：命令行脚本、定时任务、Agent 工具都想用同一段逻辑，只能复制粘贴

**分层解决的正是这三件事**：

| 好处       | 具体体现                                             |
| -------- | ------------------------------------------------ |
| **可替换**  | 想把 PostgreSQL 换成 MySQL？只改 `db/`，`services/` 一行不动 |
| **可测试**  | `app/tests/` 里 6,086 行测试，直接调 service 函数，不用起 HTTP |
| **可复用**  | 同一个 `analyze_issue()` 既被 HTTP 接口调，也被 Agent 当工具调  |
| **职责清晰** | 看到文件在哪个目录，就知道它该干什么                               |

**一个真实例子**：`IssueAgent.analyze_issue()` 在 `services/agents/issue_agent.py`，它被两处调用：

1. `POST /api/issues/{id}/analyze`（用户手动点按钮）
2. `ChatAgent` 的工具 `issue_agent.analyze_issue`（AI 自己决定调用）

如果业务逻辑写在路由里，这两处就得写两遍。分层后只写一遍。

## 4.3 数据层：`db/`（2 个文件）

### `session.py`（22 行）—— 数据库连接

```python
engine = create_engine(settings.database_url, pool_pre_ping=True)
SessionLocal = sessionmaker(bind=engine, autoflush=False, autocommit=False)

def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

三个概念：

| 概念             | 是什么                                 |
| -------------- | ----------------------------------- |
| `engine`       | 连接池，全局一个，管理所有数据库连接                  |
| `SessionLocal` | "会话工厂"，每次调用产生一个会话                   |
| `get_db()`     | FastAPI 的依赖注入函数，每个请求自动分配一个会话，用完自动关闭 |

`pool_pre_ping=True` 会在取连接前先 ping 一下，避免拿到已断开的死连接。

### `models.py`（541 行）—— 32 张表的定义

这是理解数据结构的核心文件。每张表是一个类：

```python
class Repository(Base):
    __tablename__ = "repositories"

    id: Mapped[uuid.UUID] = mapped_column(Uuid(as_uuid=True), primary_key=True, default=uuid.uuid4)
    owner: Mapped[str] = mapped_column(String(200), index=True)
    full_name: Mapped[str] = mapped_column(String(400), unique=True, index=True)
    ...

    issues: Mapped[list["Issue"]] = relationship(back_populates="repo", cascade="all, delete-orphan")
```

**怎么读这种写法**：

| 部分                                  | 含义                                  |
| ----------------------------------- | ----------------------------------- |
| `Mapped[uuid.UUID]`                 | Python 侧的类型（IDE 用）                  |
| `mapped_column(Uuid(as_uuid=True))` | 数据库侧的类型（PostgreSQL 的 UUID 列）        |
| `primary_key=True`                  | 主键                                  |
| `default=uuid.uuid4`                | 插入时自动生成 UUID                        |
| `index=True`                        | 建索引，加速查询                            |
| `unique=True`                       | 唯一约束                                |
| `nullable=True`                     | 允许为空                                |
| `ForeignKey("repositories.id")`     | 外键，指向另一张表                           |
| `relationship(...)`                 | 对象关系，`repo.issues` 直接拿到关联的 Issue 列表 |
| `cascade="all, delete-orphan"`      | 删仓库时，关联的 Issue 一起删                  |

详细表结构见第 6 章。

### ChatAgent 的推理循环（最核心机制）

它用 LangGraph 构建了一个**状态图**，只有两个节点：

```
        ┌──────────────────┐
        │  model_decision  │  ← 问 LLM：你要调工具吗？
        └────────┬─────────┘
                 │
        ┌────────▼─────────┐
        │  有 tool_calls?  │
        └────┬────────┬────┘
             │ 否     │ 是
             │        ▼
             │  ┌─────────────┐
             │  │ tool_action │  ← 执行工具，结果存为 observation
             │  └──────┬──────┘
             │         │
             │         └──→ 回到 model_decision
             ▼

```

**工具定义在哪？** 不在 `chat_agent.py` 里，而在路由层 `chat.py` 的 `_build_conversation_tools()`。

```python

    async def read_file(path: str) -> dict:
        ...
    return {"workspace.read_file": read_file, ...}
```

**为什么这样设计**：工具需要数据库会话、当前仓库、当前会话这些"上下文"。用**闭包**把 `db`/`repo`/`conversation` 捕获进去，`chat_agent.py` 就不用关心这些，只负责"把工具交给模型"。

### 一个容易误解的点：流式是"假"流式

```python
response = await tool_model.ainvoke(messages)   # 不是 astream！
```

模型调用是**一次性拿完整结果**的。所谓流式，是拿到完整答案后，**在应用层按 36 个字符切片**再推给前端：

```python
def _stream_answer(text: str):
    for i in range(0, len(text), 36):
        yield text[i:i+36]
```

**为什么这么做**：因为 Agent 循环需要完整结果才能判断"要不要继续调工具"，无法真流式。但前端需要打字机效果，所以在最后一步做了切片模拟。

### 多 Agent 工作流（WorkflowOrchestrator）

```
PlannerAgent.run(goal)
    ↓ 产出 WorkflowSpec（任务图）
_run_task_graph(spec)
    ↓ 按 dependencies 拓扑排序，asyncio.gather 并行执行
ObserverAgent.run(results)
    ↓ 校验：有冲突吗？证据够吗？置信度低吗？
    ↓ 有问题 → PlannerAgent.replan() 重新规划（最多 2 轮）
SynthesisAgent.run(...)
    ↓ 合成最终决策备忘录
```

**状态怎么传递**：不共享内存对象，全程传 **Pydantic 模型的 dict 快照**。每个任务产出 `WorkflowTaskResult`（含 `status` / `summary` / `output` / `confidence` / `citations`），下游任务读 `output`。

**依赖语义**：

- `dependencies` 全部成功 → 任务才 ready
- 依赖失败 → 后继任务标记 `skipped`
- 单任务有超时（`asyncio.wait_for`）

## 4.7 RAG 子系统：`services/rag/`（12 个文件，约 3,900 行）

### 核心认知：双存储架构

### `chunking.py` 为什么有 1038 行

因为它不是"按字数切"，而是**四种结构解析器 + 一套打包器**：

| 策略                | 做法                                 |
| ----------------- | ---------------------------------- |
| 纯文本               | 定长切 + 向前找段落边界 + 重叠                 |
| Markdown/PDF/DOCX | 维护标题栈生成 `section_path`；识别代码围栏；识别页码 |
| JSON              | 按顶层 key 拆，标注 `json_path=$.xxx`     |
| CSV               | **每块重复表头**，按行打包                    |
| 代码                | Python 用 `ast` 抽函数/类；其他语言用正则抽符号    |

**最巧妙的设计：父子块结构**

```
父块 P1（完整章节，不参与检索）
  ├── 子块 C1（检索单位）
  ├── 子块 C2
  └── 子块 C3
```

检索命中 `C2` 后，`expand_parent_context` 会把相邻的 `C1`、`C3` 一起拼回来。

**为什么**：切太碎会导致"一句话没有上下文"，切太大又检索不准。父子块同时解决两个问题。

### 混合检索的分数融合公式

```python
combined = min(1.0, 0.62 * vector_score + 0.30 * keyword_score + both_bonus)
both_bonus = 0.08 if 两路都命中 else 0.0
```

- **向量路**：Milvus COSINE 相似度，按 `repo_id` 过滤，做 max 归一化
- **关键词路**：自实现 BM25（`K1=1.5, B=0.75`），字段加权 `title 4.0 / path 3.0 / symbol 4.5 / content 1.0`
- **融合**：以 `chunk_id` 为 key 合并，两路都命中的额外加分


**为什么用混合**：向量检索擅长"语义相似"（问"鉴权"能找到"认证"），关键词检索擅长"精确匹配"（找 `AuthService.py`）。两者互补。

### `answer_gate.py`：回答前的"闸门"

它**不是检索过滤器**，而是**生成前的准入判定**，四种决策：

| 决策                      | 触发条件                                | 结果          |
| ----------------------- | ----------------------------------- | ----------- |
| `insufficient_evidence` | 无结果，或最高分低于阈值                        | 直接拒答，不调 LLM |
| `insufficient_evidence` | 强信号（`xxx.py`、`#123`、`XxxError`）全部缺席 | 直接拒答        |
| `conflict`              | 高分证据出现"允许 vs 禁止"极性冲突                | 提示存在冲突      |
| `ask_clarification`     | 问题含"这个/它"+ 多来源或过短                   | 反问用户        |

**为什么重要**：这是**防止幻觉的关键设计**。证据不够时直接说"我不知道"，而不是让 LLM 编一个答案。而且不调 LLM，省钱。

### `source_policy.py`：什么进 RAG，什么不进

```python
RAG_SOURCE_TYPES = {issue, pull_request, workflow_run, project_doc, knowledge_file, memory_note}
DIRECT_SOURCE_TYPES = {project_overview, project_manifest, team_member, weekly_report, chat_session, ...}
```

**关键设计：`code_file` 两个集合都不在！**

```python
# add_documents 里显式抛错
raise ValueError("源码必须通过工作区实时搜索，不进入向量库")
```

**为什么**：代码会天天变，向量索引一旦过期就会给出**错误答案**。所以代码走 `workspace.search_code` 实时读磁盘，永远是最新的。这是刻意的架构边界。

### MCP：跨进程的工具协议

`mcp_client.py` 启动一个**子进程**（`app/mcp/memory_server.py`），通过标准输入输出通信：

```python
class StdioMcpClient:
    def __init__(self, command: str, args: list[str]):
        ...
    async def call_tool(self, name: str, arguments: dict) -> dict:
        ...
```

**为什么用子进程而不是直接 import**：MCP（Model Context Protocol）是一个**标准协议**，任何实现了 MCP 的服务都能接入。用子进程隔离，意味着记忆服务可以独立开发、独立部署、甚至换成别的语言实现。

### 阶段 2：后端路由准备（`chat.py`）

```python
async def _conversation_sse(...):
    # ① 拿到或创建会话
    conversation = ensure_conversation(db, repo.id, payload.conversation_id)

    # ② 检查上下文压力，必要时压缩

    # ③ 存用户消息（先落库，防止后续崩溃丢失）
    message_store.append(repo_id=repo.id, conversation_id=conversation.id,
                         role="user", content=payload.message)

    # ④ 组装上下文
    assembled = ContextAssembler(db).assemble(repo, conversation, payload.message)
    #    assembled.system_context   → 系统提示 + 项目信息 + 记忆
    #    assembled.history_messages → 最近 N 条对话
    #    assembled.evidence         → 相关 Issue/PR/CI 摘要

    # ⑤ 注入 14 个工具
    context["tools"] = _build_conversation_tools(repo, conversation, db)

    # ⑥ 交给 ChatAgent
    async for event in ChatAgent().run_stream({"message": payload.message}, context):
        yield encode_sse(event["type"], event["data"])
```

**为什么第 ③ 步要先落库？** 如果第 ⑥ 步 Agent 崩溃了，用户的消息至少还在，刷新页面能看到自己问过什么。

### 阶段 3：ChatAgent 初始化（`chat_agent.py`）

```python
async def run_stream(self, input_data, context):
    # ① 激活技能
    self._activate_skills(input_data["message"], context)

    # ② 把工具包装成 LangChain 格式
    tools = self._build_langchain_tools(context["tools"])

    # ③ 检查是否需要走"短路分支"
    if self._asks_project_overview(message):
        # 预读 README / package.json，不走 LLM 循环
        ...

    # ④ 构建状态图
    graph = self._build_agent_graph()
    async for event in graph.astream(state):
        yield event
```

**四条短路分支**（不进入 LLM 循环，省钱省时间）：

| 分支                         | 触发条件                    | 处理方式                 |
| -------------------------- | ----------------------- | -------------------- |
| `direct_recent_history`    | 最近消息已足够回答（如"刚才说的第 3 点"） | 直接从历史拼答案             |
| `required_memory_tool`     | 问题明确需要记忆                | 强制预取记忆工具             |
| `_asks_project_overview()` | 问"这个项目是干什么的"            | 预读 README / manifest |
| `model is None`            | 没有配置 LLM Key            | 降级为本地证据拼接            |

### 阶段 4：LangGraph 推理循环

```
进入 model_decision 节点
    │
    ├─ 构造 messages（只有两条！）
    │    messages = [SystemMessage(system_prompt),
    │                HumanMessage(user_prompt)]
    │
    │  ⚠️ 注意：不是累积对话历史，而是每轮重建两条消息。
    │     历史、证据、工具结果全部拼进 user_prompt 这一个字符串里。
    │
    ├─ response = await tool_model.ainvoke(messages)
    │
    ├─ 检查 response.tool_calls
    │    │
    │    ├─ 空 → final_answer = response.content → 结束
    │    │
    │    └─ 非空 → pending_tool_calls = response.tool_calls
    │              → 进入 tool_action 节点
    │
    ▼
进入 tool_action 节点
    │
    ├─ 取出 pending[0]（一次只执行一个）
    ├─ 执行工具函数（await tool.ainvoke(args)）
    ├─ 结果包装成 observation，追加到 state["observations"]
    │
    ├─ pending 还有剩余 → 继续 tool_action
    └─ pending 空了 → 回到 model_decision
```

**为什么每轮重建两条消息而不是累积历史？**

这是本项目一个**很有特点的设计**。传统做法是 `messages.append(ToolMessage(...))` 让历史自然增长，但那样会导致：

- 历史无限膨胀，很快超 token 限制
- 工具返回的巨大 JSON 全塞进对话，浪费 token

本项目的做法是：**把工具结果压缩成 JSON observation，重新拼进 prompt**。这样每轮都能主动控制"给模型看什么、看多少"。

代价是：实现更复杂（要自己管 token 预算）。

### 阶段 5：工具执行（举例）

假设模型决定调用 `pr_review_agent.analyze_pr`：

```python
# chat.py 里定义的闭包
async def analyze_pr(pr_number: int) -> dict:
    pr = db.query(PullRequest).filter(...).one_or_none()   # 查数据库
    result = await PRReviewAgent().run(
        {"pr_id": str(pr.id)},
        {"repo": repo, "db": db}

```

它内部会：

1. 查 `pr_files` 表拿到 diff
2. 按文件分块（每个文件最多 N 行）
3. 用规则找出风险信号（删除了测试、改了配置、动了鉴权代码…）
4. 可选地调 LLM 做更细的分析
5. 返回结构化结果

### 阶段 6：流式输出

```python
def _stream_answer(text: str):
    chunk_size = 36
    for i in range(0, len(text), chunk_size):
        yield {"type": "delta", "data": {"text": text[i:i+chunk_size]}}
```

配合 `encode_sse`：

```python
def encode_sse(event: str, data: dict) -> str:
    return f"event: {event}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"
```

前端 `apiPostStream` 按 `\n\n` 切分事件块，逐个 `JSON.parse` 后回调。

### 阶段 7：落库

```python
if event_type == "final":
    message_store.append(role="assistant", content=final["answer"], ...)
    db.add(AgentRun(user_message=..., route=..., tool_calls=..., final_answer=...))
    touch_conversation(conversation)
    SessionSealer(db).seal(repo, conversation)   # 提炼记忆
    db.commit()
```

**`SessionSealer.seal()` 做的事**：把这一轮对话提炼成"事实/决策/待办/用户偏好"，写进 `conversation_memories` 表。这样下次对话时，Agent 能"记得"之前聊过什么。

**目标**：用户问"我们的鉴权是怎么设计的"，系统检索相关文档并带引用回答。

```

**`pipeline_trace`**：整个流程每一步都记录耗时和中间结果，存在返回值里。前端能展示"检索用了 120ms，重排用了 80ms，生成了 2.3s"，评测时也能定位是哪个环节出了问题。

## 5.5 数据流五：多 Agent 工作流

**目标**：处理"这个 PR 能合并吗"这类需要多维度判断的复杂问题。

```
ChatAgent 决定调用工具 workflow.run_engineering_review
    │
    ▼ WorkflowOrchestrator.run(goal)
┌──────────────────────────────────────────────────────┐
│ ① PlannerAgent.run(goal)                             │
│    → 产出 WorkflowSpec：                              │

│        goal: "评估 PR #12 是否可合并",                 │

│          {id:"t1", agent:"pr_review",  deps:[]},     │
│          {id:"t2", agent:"ci_debug",   deps:[]},     │
│          {id:"t3", agent:"repo_health",deps:[]},     │
│          {id:"t4", agent:"safety",     deps:["t1","t2"]}│
│        ]                                             │
│      }                                               │
│                                                      │
│ ② _run_task_graph(spec)                              │
│    按 dependencies 拓扑排序，同层用 asyncio.gather 并行 │
│    t1 / t2 / t3 并行跑 → 都完成后才跑 t4              │
│    每个任务产出 WorkflowTaskResult                     │
│                                                      │
│ ③ ObserverAgent.run(results)                         │
│    纯规则校验：                                        │
│    ├─ 有没有冲突？（PR 说没问题，CI 说失败）            │
│    ├─ 证据够不够？                                     │
│    ├─ 置信度低不低？                                   │
│    └─ 算 overall_confidence                          │
│                                                      │
│ ④ 需要重规划？                                        │
│    原因 = task_error / evidence_gap / low_confidence  │
│    有原因 → PlannerAgent.replan() → 回到 ②（最多 2 轮）│
│    且新旧任务图签名相同则停止（防死循环）                │
│                                                      │
│ ⑤ SynthesisAgent.run(...)                            │
│    纯模板拼装 → 决策备忘录                             │
│    ⚠️ 不调 LLM，只是把结构化结果排版                     │
└──────────────────────────────────────────────────────┘
    │
    ▼ 写入 agent_workflow_runs + agent_task_runs 两张表
    ▼ 返回 WorkflowReport 给 ChatAgent
```

**为什么 Synthesis 不调 LLM？**
因为前面几个 Agent 已经产出了结构化结论。合成阶段只需要"排版"，不需要再"思考"。省一次 LLM 调用，也避免引入新的幻觉。

**为什么用拓扑排序而不是固定顺序？**
任务之间有真实依赖（安全评估必须在 PR 审查和 CI 诊断之后）。拓扑排序能自动算出"哪些能并行、哪些必须等"，既正确又快。

32 张表看着吓人，但按业务分成 8 组就清楚了：

| 组 | 表 | 数量 |
|---|---|---|

| **对话与消息** | `conversations`、`chat_messages`、`chat_sessions`、`agent_runs` | 4 |

| **RAG 与知识** | `documents`、`knowledge_base_configs`、`knowledge_source_documents`、`retrieval_test_runs`、`knowledge_graph_edges` | 5 |

| **工作流与评测** | `agent_workflow_runs`、`agent_task_runs`、`eval_runs`、`analysis_results` | 4 |

## 6.2 核心表关系

```
users

  ├──< workspaces

repositories  ← 全系统的中心，几乎所有表都挂在它下面

  ├──< issues
  ├──< pull_requests
  │      ├──< pr_files
  │      └──< pr_review_comments

  │      ├──< chat_messages
  │      ├──< chat_sessions
  │      ├──< conversation_memories

  │      └──< agent_task_runs
  ├──< action_drafts
  └──< chat_feedback

**记住一句话**：`repositories` 是根，其他几乎都是它的子表。

## 6.3 七张最该先看懂的表

### ① `repositories` —— 一切的中心

```python
id, owner, name, full_name, provider, local_path, checkout_mode,
github_token_encrypted, default_branch, last_sync_at, created_at
```

`checkout_mode` 有三个值：`managed`（系统克隆）、`local`（用你本地路径）、`remote`（只读 API）。

### ② `chat_messages` —— 对话记录

```python
id, repo_id, conversation_id, role, content, route, tool_calls(JSON), metadata(JSON)
```

`role` 是 `user` / `assistant`。`tool_calls` 用 JSON 存这一轮调了哪些工具。

**为什么用 JSON 而不是单独建表？** 因为工具调用的结构会变（不同工具参数不同），用 JSON 更灵活。代价是没法直接用 SQL 查"哪个工具被调最多"，需要应用层处理。

### ③ `documents` —— RAG 的事实源

```python
id, repo_id, source_type, source_id, title, content(Text), metadata(JSON)
```

**关键**：`content` 存**完整正文**（Text 类型，不限长度）。Milvus 里只存截断版。

`source_type` 决定了它来自哪：`issue` / `pull_request` / `workflow_run` / `project_doc` / `knowledge_file` / `memory_note`。

### ④ `knowledge_base_configs` —— 每个仓库一份配置

```python
repo_id(unique), embedding_provider, embedding_model, embedding_dimensions,
retrieval_method, rerank_enabled, top_k, score_threshold, chunk_size, chunk_overlap
```


**为什么每个仓库单独配置**：不同项目的文档特点不同。代码库适合小 chunk，手册适合大 chunk。

**重要约束**：所有共享同一个 Milvus collection 的仓库，**必须用同一个 embedding 模型和维度**。`embeddings.validate_embedding_contract()` 会强校验这一点——因为不同模型的向量空间不可比，混在一起检索结果是错的。

### ⑤ `action_drafts` —— 写操作的闸门

```python
id, repo_id, draft_type, target_type, target_id, title, content,
risk_level, status, created_by, confirmed_by, executed_at, execution_result
```

`status` 流转：`pending_confirmation` → `confirmed` → `executed` / `failed`。

**这是本项目的安全核心**：AI 想改 GitHub 上的东西，不能直接改，必须先产出草稿，人工点确认才执行。

### ⑥ `agent_workflow_runs` + `agent_task_runs` —— 工作流留痕

主表存整体（goal / spec_json / observation_json / final_answer / metrics），子表存每个任务（task_id / agent_name / status / result_json）。

**为什么分两张表**：一次工作流可能跑 5 个任务，要能单独看每个任务的耗时和结果。

### ⑦ `audit_logs` —— 审计

```python
user_id, repo_id, action, target_type, target_id, status, request_json, result_json
```

所有敏感操作（确认草稿、删仓库、改配置）都写一条。出了问题能追溯"谁在什么时候干了什么"。

## 6.4 三个值得注意的设计细节

### 细节一：为什么大量用 JSON 字段

```python
labels: Mapped[list[str]] = mapped_column(JSON, default=list)
tool_calls: Mapped[list[dict]] = mapped_column(JSON, default=list)
meta: Mapped[dict] = mapped_column("metadata", JSON, default=dict)
```

**好处**：结构灵活，加字段不用改表
**代价**：不能建索引、不能用 SQL 精确查询、数据一致性靠应用层保证

**判断标准**：需要频繁按某字段查询/排序 → 建独立列；只是"顺带存一下" → 用 JSON。

### 细节二：`meta` 字段映射到 `metadata` 列名

```python
meta: Mapped[dict[str, Any]] = mapped_column("metadata", JSON, default=dict)
```

**为什么**：`metadata` 在 SQLAlchemy 里是**保留字**（`Base.metadata` 是表注册表），Python 属性名不能叫 `metadata`，所以属性叫 `meta`，列名仍叫 `metadata`。

### 细节三：级联删除

```python
issues: Mapped[list["Issue"]] = relationship(
    back_populates="repo",
    cascade="all, delete-orphan"
)
```

删一个 Repository，它下面所有 Issue 自动删。**但注意**：Milvus 里的向量**不会**自动删，必须在 `repos.py` 的删除逻辑里手动清理（代码里确实做了）。

### `apiPostStream` 的实现（关键）

浏览器原生的 `EventSource` 只支持 GET，但聊天需要 POST（要传消息体）。所以这里**手写解析**：

```ts
const reader = response.body.getReader();
const decoder = new TextDecoder();
let buffer = "";

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });

  const events = buffer.split("\n\n");   // SSE 用空行分隔事件
  buffer = events.pop() ?? "";            // 最后一段可能不完整，留到下次

  for (const rawEvent of events) {
    const lines = rawEvent.split("\n");
    const event = lines.find(l => l.startsWith("event: "))?.slice(7) ?? "message";
    const dataText = lines.filter(l => l.startsWith("data: "))
                          .map(l => l.slice(6)).join("\n");
    if (dataText) onEvent(event, JSON.parse(dataText));
  }
}
```

**核心技巧**：`buffer.split("\n\n")` 之后，**最后一段可能是半个事件**（网络分包），所以 `pop()` 出来留到下一轮。这是流式解析的标准写法。

# 第 8 章 设计意图：为什么这样写

这一章回答"为什么"，是全文最有价值的部分。看懂这些，你不仅知道代码在做什么，还知道**为什么不能随便改**。

## 8.1 为什么代码文件不进 RAG

`source_policy.py` 里明确把 `code_file` 排除在 RAG 之外，甚至 `add_documents` 会**主动抛错**：

```python
raise ValueError("源码必须通过工作区实时搜索，不进入向量库")
```

**原因**：向量索引是"快照"。你今天索引了 `auth.py`，明天同事改了鉴权逻辑，索引还是旧的。用户问"鉴权怎么做的"，RAG 会自信地给出**过时的错误答案**——这比说"不知道"危险得多。

**替代方案**：`workspace.search_code` 直接读磁盘上的当前文件。永远最新。

**通用原则**：**会频繁变化的数据不要做向量索引**。向量检索适合"相对稳定的知识"（文档、规范、历史 Issue），不适合"当前状态"（代码、配置、库存）。

## 8.2 为什么所有写操作必须过草稿

`ActionDraft` 的设计：AI 想改 GitHub → 生成草稿 → 人工确认 → 才执行。

**原因**：LLM 会犯错。如果 AI 直接能关 Issue、改 PR、加标签，一次幻觉就可能造成真实损害（关错 Issue、误删分支）。

**代价**：多一步人工操作，体验变慢。

**判断**：这个取舍在"AI 辅助研发"场景是**正确的**——研发流程本来就需要 review，多一次确认不增加负担，但避免了事故。

**实现细节**：`risk_level` 字段让高风险操作更醒目；`audit_logs` 记录谁确认的；`execution_result` 存执行结果，失败可追溯。

## 8.3 为什么 RAG 要"双存储"

PostgreSQL 存全文，Milvus 存向量。

**原因一：Milvus 字段有长度限制**
```python
content: 8192 字节（UTF-8 截断）
metadata_json: 4096 字节
```

一篇 5000 字的中文文档约 15000 字节，Milvus 存不下。所以 Milvus 只存"够用来检索和预览"的部分，完整正文回 PostgreSQL 取。

**原因二：职责分离**
- Milvus 擅长"找相似的"（向量计算）
- PostgreSQL 擅长"精确查、事务、关联"（`WHERE repo_id = ? AND source_type = ?`）

**原因三：可重建**
Milvus 挂了，可以从 PostgreSQL 的 `documents` 表重新生成所有向量。反之不成立。

**通用原则**：**向量库是索引，不是数据源**。真相永远在关系型数据库里。

## 8.4 为什么切片要分父子块

```
父块 P1（整章，不参与检索）
  ├── 子块 C1（检索单位，约 800 字）
  ├── 子块 C2
  └── 子块 C3
```

**问题**：切太碎 → 检索准，但拿到的一小段缺上下文；切太大 → 上下文完整，但向量被"平均"了，检索不准。

**解法**：用小块检索，用大块喂给模型。命中 `C2` 后，把相邻的 `C1`、`C3` 拼回来。

**代价**：切片逻辑复杂（`chunking.py` 1038 行的主要原因），存储翻倍。

**这是 RAG 领域的标准解法**，叫 "small-to-big retrieval" 或 "parent document retriever"。

## 8.5 为什么用混合检索而不是纯向量

```python
combined = 0.62 * vector_score + 0.30 * keyword_score + 0.08 * both_bonus
```

**向量检索的强项**：语义相似。问"鉴权"能找到写着"认证"的段落。
**向量检索的弱项**：精确匹配。找 `AuthService.py` 这个具体文件名，向量可能找不到，因为文件名没有"语义"。

**关键词检索（BM25）正好互补**：精确匹配强，语义理解弱。

**`both_bonus` 的作用**：两路都命中的结果，可信度显著更高，所以额外加 0.08 分。

**为什么权重是 0.62 / 0.30**：这是经验值。向量检索在语义问答场景通常更重要，但不能完全丢掉关键词（专有名词、代码标识符必须精确匹配）。

## 8.6 为什么"流式"是假的

```python
response = await tool_model.ainvoke(messages)   # 不是 astream
# ...
for i in range(0, len(text), 36):
    yield text[i:i+36]
```

**原因**：Agent 循环需要**完整**的模型输出来判断 `tool_calls` 是否为空。如果流式接收，你没法在"说到一半"时就知道"它要不要调工具"。

**所以**：必须等模型说完，再切片推给前端。

**代价**：首字延迟变高（要等完整生成）。**收益**：循环逻辑简单可靠。

**这是一个典型的工程取舍**：真实时性 vs 实现复杂度。对于"Agent 要调 5 个工具"的场景，用户本来就要等，首字延迟不是瓶颈。

## 8.7 为什么上下文压缩要分三层

| 层 | 位置 | 做什么 |
|---|---|---|
| 上游装配层 | `chat.py` → `ProgressiveContextManager.ensure_headroom()` | 请求前检查，快满了就压缩旧消息 |
| Agent 投影层 | `chat_agent.py` → `_runtime_tool_context()` | 按 token 预算，从最新往前保留 observation，超出的标记为 `omitted` |
| 反应式兜底 | `chat_agent.py` 捕获 `is_context_overflow_error()` | 真溢出了，用 `aggressive=True` 重建 prompt 重试一次 |

**为什么三层而不是一层**：

- 只有上游压缩 → 工具返回巨大结果时还是会溢出
- 只有 Agent 投影 → 历史消息没人管，越积越多
- 只有反应式 → 每次都要先失败再重试，浪费一次调用

三层各管一段，覆盖了"预防 / 控制 / 兜底"。

**`CONTEXT_*` 那一堆环境变量就是这三层的参数**（预算比例、保留条数、压缩阈值）。

## 8.8 为什么 Agent 用"图"而不是 while 循环

```python
graph = self._build_agent_graph()   # LangGraph
```

**while 循环也能实现工具调用**，但用图有三个好处：

1. **状态显式**：`ConversationState` 是 TypedDict，里面有什么一目了然
2. **可中断/可恢复**：图可以在任意节点暂停（LangGraph 的 checkpoint 能力）
3. **可观测**：每个节点的进出都能挂回调，方便做 trace

**代价**：引入框架依赖，调试时要理解 LangGraph 的概念。

**对本项目**：因为有 `agent_events`（记录每个决策和工具调用）和流式输出需求，用图更合适。

## 8.9 为什么 LLM 失败不抛异常

`llm/client.py` 的 `chat_json`：

```python
try:
    ...
    return json.loads(content)
except (httpx.HTTPError, KeyError, IndexError, TypeError, ValueError):
    return {}      # 返回空字典，不抛
```

**原因**：这个项目的定位是"**LLM 是增强，不是依赖**"。所有 Agent 都有"规则兜底"路径：

```python
llm_result = await llm.chat_json(...)      # 可能返回 {}
if llm_result:
    return llm_result                       # 有就用
return self._rule_based_analysis(...)      # 没有就走规则
```

**收益**：即使 LLM API 完全挂掉，系统仍然可用（只是分析质量下降）。这对演示和答辩非常重要——不会因为网络问题当场翻车。

**代价**：LLM 出错时**静默降级**，用户不知道"这次结果是规则算的"。所以代码里会记录 `model_name` 字段来区分。

## 8.10 为什么每轮重建两条消息

```python
messages = [SystemMessage(content=system_prompt),
            HumanMessage(content=user_prompt)]
```

而不是 `messages.append(ToolMessage(...))` 累积。

**原因**：
1. **token 可控**：每轮都重新计算预算，精确控制"给模型看多少"
2. **避免工具结果污染**：工具返回的巨大 JSON 不必全塞进对话历史
3. **压缩更简单**：不用在历史里找"哪些 ToolMessage 可以删"

**代价**：每轮都要重新序列化所有 observation，有 CPU 开销（但相比 LLM 调用可忽略）。

**这是一个不太常见的做法**（主流框架都是累积式），但在这个项目"要严格控制 24000 token 预算"的需求下是合理的。

# 第 9 章 代码风格与约定

## 9.1 命名约定

| 类型 | 风格 | 例子 |
|---|---|---|
| 文件/模块 | 全小写 + 下划线 | `chat_memory.py`、`code_search.py` |
| 类 | 大驼峰 | `ChatAgent`、`ContextAssembler` |
| 函数/变量 | 全小写 + 下划线 | `analyze_issue`、`system_context` |
| 常量 | 全大写 + 下划线 | `ROLE_PERMISSIONS`、`RAG_SOURCE_TYPES` |
| 私有成员 | 前导下划线 | `_build_conversation_tools`、`_derive_demo_key` |

**看到 `_` 开头就知道**：这是内部实现，外部不应该调用。

**工具名用点号分层**：`workspace.read_file`、`issue_agent.analyze_issue`。这是为了给 LLM 看的——点号让它更容易理解"这是哪个模块的什么能力"。

## 9.2 错误处理的三种模式

### 模式一：抛 HTTPException（路由层）

```python
if repo is None:
    raise HTTPException(status_code=404, detail="未找到仓库")
```

**适用**：需要告诉用户"哪里错了"的场景。FastAPI 会自动转成 JSON 响应。

### 模式二：返回空值（LLM 调用）

```python
except (httpx.HTTPError, KeyError, IndexError, TypeError, ValueError):
    return {}
```

**适用**：有降级路径的"增强型"依赖。见 8.9。

### 模式三：自定义异常（关键资源）

```python
class MilvusUnavailableError(RuntimeError):
    pass
```

配合 `main.py` 的全局处理器转成 503。**适用**：需要特殊状态码或特殊处理的错误。

## 9.3 依赖注入的两种用法

### 数据库会话

```python
async def list_repos(db: Session = Depends(get_db)):
```

每个请求一个会话，结束自动关闭。

### 权限校验

```python
async def create_workspace(
    user: User = Depends(require_permission("settings:manage")),
):
```

`require_permission()` 返回一个**函数**（闭包），FastAPI 会调用它。没权限直接 403，根本不会进入路由函数体。

**这种"装饰器式"的权限检查**比在每个函数开头写 `if not has_permission(...)` 更干净。

## 9.4 统一的返回值契约

Agent 和工具都返回这个结构：

```python
{
    "route": "pr_review",           # 走了哪条处理路径
    "answer": "文本回答",            # 给人看的
    "tool_calls": [...],            # 调了什么工具
    "citations": [...],             # 引用来源
    "retrieved_contexts": [...],    # 仅 RAG 有
}

```

**为什么统一**：路由层、前端、评测系统都按这个结构消费，不用为每个 Agent 写一套解析逻辑。

`route` 字段尤其有用——出问题时能一眼看出"这次走的是哪条分支"。

## 9.5 类型注解的严格程度

项目**全量使用类型注解**，但**不做运行时强制校验**（除了 Pydantic 模型）。

| 位置 | 注解情况 |
|---|---|
| 函数参数和返回值 | 100% 标注 |
| 类属性 | 100% 标注（SQLAlchemy 的 `Mapped[...]`） |
| 局部变量 | 很少标注（靠推断） |

**好处**：IDE 能全程补全和跳转，重构时不会漏改。

## 9.6 文件组织的隐含规则

观察 `services/` 的目录结构，能看出三条规则：

1. **一个业务概念一个文件**：`repos_sync.py`、`chat_memory.py`、`code_search.py`
2. **超过 500 行就拆目录**：`agents/`、`rag/`、`evals/`、`github/` 都是这样来的
3. **子目录用 `__init__.py` 标记为包**（虽然内容是空的）

**例外**：`chat_agent.py` 2066 行、`chat.py` 1806 行、`app/page.tsx` 5933 行都没拆。这是**技术债**——功能堆得太快，来不及重构。

# 第 10 章 如何自己动手改

## 10.1 加一个新的 API 接口

**需求举例**：加一个 `GET /api/repos/{id}/stats` 返回仓库统计。

### 步骤

**① 在 `schemas/` 定义响应结构**（`schemas/repos.py`）

```python
from pydantic import BaseModel

class RepoStats(BaseModel):
    issue_count: int
    pr_count: int
    workflow_run_count: int
```

**② 在 `services/` 写业务逻辑**（新建 `services/repo_stats.py`）

```python
from sqlalchemy.orm import Session
from app.db.models import Issue, PullRequest, WorkflowRun

def compute_stats(db: Session, repo_id) -> dict:
    return {
        "issue_count": db.query(Issue).filter(Issue.repo_id == repo_id).count(),
        "pr_count": db.query(PullRequest).filter(PullRequest.repo_id == repo_id).count(),
        "workflow_run_count": db.query(WorkflowRun).filter(WorkflowRun.repo_id == repo_id).count(),
    }
```

**③ 在路由里加接口**（`api/routes/repos.py`）

```python
from app.schemas.repos import RepoStats
from app.services.repo_stats import compute_stats

@router.get("/{repo_id}/stats", response_model=RepoStats)
async def get_repo_stats(repo_id: UUID, db: Session = Depends(get_db)):
    repo = db.get(Repository, repo_id)
    if repo is None:
        raise HTTPException(status_code=404, detail="未找到仓库")
    return compute_stats(db, repo_id)
```

**④ 重启后端**（`.env` 和代码改动都要重启才能生效——`--reload` 对 `.py` 有效，但保险起见重启一次）

**⑤ 验证**：打开 `http://localhost:8000/docs`，找到新接口点 "Try it out"。

> 注意：`{repo_id}/stats` 这种路径要放在 `{repo_id}` 这类通配路由**之前**定义，否则会被抢先匹配。

## 10.2 给 Agent 加一个新工具

**需求举例**：让 AI 能查"这个仓库有多少未关闭的 Issue"。

### 步骤

**① 在 `chat.py` 的 `_build_conversation_tools()` 里加闭包**

```python
def _build_conversation_tools(repo, conversation, db):
    async def read_file(path: str) -> dict:
        ...

    # 新增这个
    async def count_open_issues() -> dict:
        from app.db.models import Issue
        count = db.query(Issue).filter(
            Issue.repo_id == repo.id,
            Issue.state == "open",
        ).count()
        return {
            "route": "repo_stats",
            "answer": f"当前有 {count} 个未关闭的 Issue",
            "tool_calls": [],
            "citations": [],
        }

    return {
        "workspace.read_file": read_file,
        "repo_stats.count_open_issues": count_open_issues,   # 注册
        ...
    }
```

**② 在 `chat_agent.py` 的 `available_tools` 里声明**

找到 `self.available_tools` 的定义（一个 dict），加入：

```python
"repo_stats.count_open_issues": {
    "description": "统计当前仓库未关闭的 Issue 数量。当用户问'有多少待处理问题'时使用。",
    "parameters": {"type": "object", "properties": {}, "required": []},
},
```

**关键**：`description` 写得越清楚，模型越知道什么时候该调它。这是"提示工程"的一部分。

**③ 重启后端，测试**

在聊天框问"这个仓库有多少待处理的 Issue"，观察前端是否出现 `repo_stats.count_open_issues` 的工具卡片。

### 工具设计的三个要点

| 要点 | 说明 |
|---|---|
| **description 要具体** | 写清"什么时候用"，不要只写"查询统计" |
| **参数要少** | 参数越多，模型越容易传错 |
| **返回结构要统一** | 必须含 `route` / `answer` / `tool_calls` / `citations` |

## 10.4 调试技巧：怎么快速定位问题

### 问题一：接口报 500，不知道哪里错了

**方法**：看后端终端的 traceback。FastAPI 会把完整调用栈打出来。

如果 `--reload` 模式下日志被刷掉了，去 `http://localhost:8000/docs` 重新触发一次，盯着终端。

### 问题二：AI 回答不对，不知道它调了什么工具

**方法一**：前端看工具卡片（`tool_use` / `tool_result` 事件）。
**方法二**：查数据库：

```bash
docker exec -it devflow-ai-postgres psql -U devflow -d devflow -c \
  "SELECT route, tool_calls, final_answer FROM agent_runs ORDER BY created_at DESC LIMIT 3;"
```

`tool_calls` 字段是 JSON，能看到完整调用链。

**方法三**：`GET /api/chat/trace/{run_id}` 拿完整 trace。

### 问题三：RAG 检索不到东西

**排查顺序**：

1. **文档处理完了吗**？
   ```bash
   docker exec -it devflow-ai-postgres psql -U devflow -d devflow -c \
     "SELECT name, status, chunk_count, error_message FROM knowledge_source_documents ORDER BY created_at DESC LIMIT 5;"
   ```
   如果 `status='failed'`，看 `error_message`。

2. **Milvus 里有向量吗**？
   ```bash
   curl -s http://localhost:9091/healthz     # 应该返回 OK
   ```

3. **是分数阈值太高吗**？
   `knowledge_base_configs.score_threshold` 默认 0.8。如果文档质量一般，很多结果会被过滤掉。可以调低到 0.5 试试。

4. **embedding 维度对得上吗**？
   如果 `EMBEDDING_DIMENSIONS` 改过但没重建索引，会报维度不匹配。

### 问题四：改了 `.env` 没生效

**原因**：配置只在启动时读一次。
**解决**：重启后端（`Ctrl+C` 后重新启动）。`--reload` 只监听 `.py` 文件，不监听 `.env`。

### 问题五：前端改了不生效

**原因**：如果是 `NEXT_PUBLIC_*` 变量，它们是**构建时**注入的。
**解决**：重启 `npm run dev`。

# 附录 A：Java 开发者对照表

> 如果你之前写 Java（Controller / Service / DAO / Entity），这一节能让你在 10 分钟内把心智模型迁移过来。

## A.1 注解级对照

| Spring / Java | Python / FastAPI | 位置 |
|---|---|---|
| `@SpringBootApplication` | `FastAPI(...)` + `create_app()` | `main.py` |

## A.2 三处"对不上"的地方

### 差异 1：没有 DAO 层（最大不同）

**Java 的三层调用**：

```java
@GetMapping("/{id}/issues")
public List<IssueDTO> list(@PathVariable UUID id) {
    return repoService.listIssues(id);        // Controller → Service
}

@Service
public class RepoService {
    @Autowired private IssueRepository repo;
    public List<IssueDTO> listIssues(UUID id) {
        return repo.findByRepoId(id);          // Service → DAO
    }
}

public interface IssueRepository extends JpaRepository<Issue, UUID> {
    List<Issue> findByRepoId(UUID repoId);     // DAO 只声明
}
```

**这个项目的实际写法**（`api/routes/issues.py`）：

```python
@router.get("/repos/{repo_id}/issues")
async def list_issues(repo_id: UUID, db: Session = Depends(get_db)):
    return (
        db.query(Issue)                        # ← Controller 直接查库
        .filter(Issue.repo_id == repo_id)
        .order_by(Issue.number.desc())
        .all()
    )
```

**统计**：路由层 104 次 `db.query`，服务层约 118 次。**全项目没有 Repository 抽象。**

**为什么可以这样**：

| 原因 | 说明 |
|---|---|
| SQLAlchemy 的 `Session` 本身就是"工作单元" | 已封装连接、事务、身份映射，再包一层 Repository 是重复抽象 |
| Python 不强制"接口 + 实现"分离 | 不需要 `IssueRepository` + `IssueRepositoryImpl` 两个文件 |
| 查询是链式 API 而非"方法名派生" | `db.query(Issue).filter(...)` 已足够表达，不需要 `findByRepoIdAndState` |

**代价**：SQL 逻辑分散。**这是本项目的技术债**，不是最佳实践。

### 差异 2：没有接口/实现分离

Java 里常见 `PaymentService` + `AlipayServiceImpl`。这个项目几乎不这么写。

全项目只有一处抽象基类（`services/agents/base.py`）：

```python
class BaseAgent(ABC):
    @abstractmethod
    async def run(self, input_data: dict, context: dict) -> dict: ...
```

**原因**：Python 是鸭子类型——"长得像鸭子就是鸭子"，不需要先声明接口。

**实际影响**：搜代码时不要找 `XxxImpl`，直接找 `xxx.py`。

### 差异 3：依赖注入是"函数级"，不是"容器级"

**Java**：Spring 启动时扫描 `@Component`，建全局 Bean 容器，`@Autowired` 从容器取。

**Python**：

```python
async def list_issues(
    repo_id: UUID,
    db: Session = Depends(get_db),                          # 每请求现造
    user: User = Depends(require_permission("repo:read")),   # 每请求现查
):
```

`Depends()` 是**按需调用一个函数**，没有全局容器，没有 Bean 生命周期。

**好处**：不用理解 singleton / prototype / request 作用域
**代价**：没有 AOP 切面，日志和事务都要手写

## A.3 需要新学的只有 3 个概念

| # | 概念 | 一句话 |
|---|---|---|
| 1 | **Session 即工作单元** | 不要找 DAO。`db.query(X).filter(...)` 就是数据访问，可以出现在 Service，简单场景也可以在路由 |
| 2 | **`Depends()` 是函数调用，不是 Bean 注入** | 每次请求都会真的执行 `get_db()`，没有单例池 |
| 3 | **模块级对象 = 单例** | `settings = Settings()` 写在模块顶层，import 一次就全局共享（相当于 `@Bean @Singleton`） |

## B.0 总览：为什么这样分目录

这个项目的分目录遵循 **5 条原则**：

| 原则 | 体现 |
|---|---|
| **① 按"技术角色"分顶层，不按"业务功能"分** | `api/` `services/` `db/` `schemas/` `core/` 都是技术角色；具体业务（Issue、PR、RAG）放在 `services/` **内部** |
| **② 一个业务概念一个文件** | `repos_sync.py`、`chat_memory.py`、`code_search.py` |
| **③ 超过 ~500 行就拆子目录** | `agents/`(13) `rag/`(12) `evals/`(3) `github/`(4) `llm/`(3) 都是这么来的 |
| **④ 子目录 = 一个内聚的子系统** | `rag/` 里的 12 个文件只服务 RAG，彼此强关联 |
| **⑤ 位置决定依赖方向** | `db/` 最底层，`core/` 横切，`api/` 最上层。**下层永远不 import 上层** |

**对比 Java 习惯**：Java 常按 `controller/` `service/` `dao/` `entity/` 平铺，然后在 `service/` 里按业务再分。这个项目把"按技术角色"和"按业务子系统"两个维度**混用**了——顶层按技术角色，`services/` 内部按业务拆子目录。

## B.3 `db/` —— 数据层（2 个文件）

**为什么只有 2 个文件**：因为这里**只管"表长什么样"和"怎么连"**，不管怎么查（查询散在业务层）。

| 文件 | 行数 | 干什么 | 为什么在这里 |
|---|---|---|---|
| `models.py` | 541 | 32 张表的 ORM 定义（字段、索引、外键、关系、级联） | 所有表集中一个文件，便于一眼看全数据模型。**没有按业务拆**，因为表之间关联紧密，拆开会增加跳转成本 |
| `session.py` | 22 | 创建 `engine`（连接池）、`SessionLocal`（会话工厂）、`get_db()`（FastAPI 依赖）、`Base`（ORM 基类） | 连接管理属于数据层基础设施 |

> **Java 类比**：`models.py` = 所有 `@Entity` 类；`session.py` = `DataSource` + `SqlSessionFactory`

**为什么单独建子目录**：RAG 是**独立的子系统**，有自己的流水线（解析→切片→向量化→存储→检索→重排→问答），内部高度内聚，对外只暴露 `knowledge_base.py` 和 `qa.py`。

| `document_processing.py` | 150 | 上传流水线编排 + 状态机（queued→parsing→splitting→embedding→completed） | **入口 1 的调度器** |
| `chunking.py` | 1038 | 结构感知切片：文本/Markdown/JSON/CSV/代码 五种策略 + 父子块打包 | 流水线第 2 步 |

| `vector_store.py` | 520 | Milvus 读写 + 与 PostgreSQL 双写 | 流水线第 4 步 |

| `source_policy.py` | 57 | 白名单：哪些数据进 RAG、哪些走直查 | **策略层**，被上面几个文件共同调用 |
| `knowledge_base.py` | 384 | 知识库配置管理 + 检索总编排 | **总导演**，串起检索全流程 |
| `retrieval.py` | 685 | 混合召回（向量 + BM25）+ 分数融合 + 去重 + 父块扩展 | 检索第 1 步 |

| `answer_gate.py` | 131 | 回答前的证据准入判定（answer / 拒答 / 冲突 / 反问） | 检索第 3 步，**生成前闸门** |

**为什么 `source_policy.py` 只有 57 行却独立成文件**：因为它是**架构边界的显式声明**——"代码文件不进 RAG"这条规则必须单独、显眼、可查。

## B.16 归类原则总结：一句话判断"该放哪"

遇到新文件，按这个顺序判断：

```
① 它定义"数据的形状"吗？        → schemas/
② 它定义"数据库的表"吗？        → db/models.py
③ 它是 HTTP 接口吗？            → api/routes/
④ 它是配置/加密/日志等横切能力吗？ → core/
⑤ 它是外部系统的适配器吗？        → services/<外部系统名>/
⑥ 它是一个完整的独立子系统吗？     → services/<子系统名>/
⑦ 它是"一个业务概念"的实现吗？     → services/<概念名>.py
```

**反例检查**：如果一个文件同时干了两件事（比如既解析 PDF 又调 LLM），就该拆成两个文件——**这就是 `document_extraction.py` 和 `qa.py` 分开的原因**。
