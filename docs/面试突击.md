# 面试突击手册（DevFlow / MergeGate）

> 用法：**不要从头读**。先看 §0 的 90 分钟路线，按顺序过。
> 每题都给「30 秒版答案」+「关键词」+「可能的追问」。关键词是用来救场的——忘了原话就想起关键词。

## §0 90 分钟突击路线

| 轮次 | 时间 | 做什么 | 目标 |
|---|---|---|---|
| 第 1 轮 | 0–35 min | §1 必背 12 题，每题**出声说一遍** | 前 3 题能不看稿说满 30 秒 |

## §1 必背 12 题

### Q1. 简单介绍一下这个项目

**30 秒版**

> 这是一个面向 GitHub 研发协作的 AI Agent 系统。研发协作的痛点是信息太散——判断一个 PR 能不能合，要翻代码、Review 意见、CI 日志、关联 Issue、项目文档，五个地方。
>
> 我把这些信息统一接进来，让 Agent 做第一轮分析：Issue 分诊、PR 审查、CI 排障，答案都带引用，能指回具体的 Issue 或文件。
>
> 关键是**AI 不能直接改 GitHub**：所有写操作先生成草稿，人工确认后才执行，全程审计。

**关键词**：信息散 → 统一接入 → Agent 第一轮分析 → 带引用 → 人工确认才写回

**追问**：规模多大？→ 104 个接口、32 张表、14 个工具、209 个测试。

---

### Q2. 和普通 Coding Agent / Copilot 有什么区别？

**30 秒版**

> 三个区别。
>
> 第一，**回答基于证据**。Copilot 补全代码，我这个是回答问题，而且每个结论要能指回具体的 Issue、文件或 CI 日志，答不出来就说"证据不足"，不硬编。
>
> 第二，**不碰你的代码**。我不改代码，只做判断和起草——判断这个 PR 能不能合、这个 CI 为什么挂。
>
> 第三，**写操作有人工闸门**。要评论、打标签、关 Issue，AI 只能起草，人签字才生效。

**关键词**：证据化 / 不改代码 / 人工闸门

> ⚠️ 这题是**分水岭**。答得好，面试官会觉得你想清楚了；答成"我的 Agent 也能改代码"，就掉进 Copilot 的赛道被比下去。

### Q3. 整体架构怎么设计的？

**30 秒版**（边画边说，画五层）

> 五层。
>
> **接入层**：GitHub API 同步 Issue/PR/CI，本地工作区读代码。
> **数据层**：Postgres 存事实，Milvus 存向量，32 张表按 `repo_id` 隔离。
> **能力层**：RAG 检索、代码图谱、MCP 记忆工具。
> **Agent 层**：ChatAgent 做总调度，下面挂 Issue/PR/CI 三个专用 Agent，再加 Planner/Observer/Synthesis 做多 Agent 编排。
> **接口层**：FastAPI 104 个接口，SSE 推流。

**关键词**：接入 → 数据 → 能力 → Agent → 接口

**追问**：为什么分这么多层？→ 因为上层只负责交互，中层负责调度判断，下层负责证据和记忆。改检索不影响 Agent。

### Q4. 几个 Agent 怎么分工？

**30 秒版**

> 一个总调度 + 三个专科 + 三个编排角色。
>
> **ChatAgent** 是总调度，14 个工具，根据问题自己选工具。
> **Issue / PR / CI 三个专用 Agent** 各自只干一件事，Prompt 和输出结构都是定制的。
> **Planner** 拆任务、**Observer** 交叉检查、**Synthesis** 汇总结论——这三个只在复杂问题上出场。
>
> 简单问题走 ChatAgent 单循环，复杂问题才升级成多 Agent 工作流。**不是所有问题都值得拆**。

**关键词**：1 调度 + 3 专科 + 3 编排；简单走单循环，复杂才拆

### Q5. 你在项目里是什么角色？

**⚠️ 这题最危险。先说清楚你的真实情况再选话术。**

| 你的实际情况 | 该怎么说 | 不能说 |
|---|---|---|
| 代码是你自己一行行写的 | "独立完成，从数据接入到 Agent 编排全链路" | — |
| 跟着课程实现，自己加了扩展 | "**跟着课程从零实现了全链路**，之后我做了三个扩展：X、Y、Z" | ❌ "我从 0 到 1 设计了整个系统" |
| 只做了部分模块 | "我主要负责 A 和 B，C 部分是参考课程实现的" | ❌ 把别人的模块说成自己的 |

**安全说法**（不管哪种情况都能用）：

> 这个项目是我独立实现的一条完整链路，从 GitHub 数据同步、RAG 检索、Agent 循环到人工确认闸门。做的时候我刻意在每个环节都停下来问"为什么这么设计"——比如为什么源码不进向量库、为什么每轮只重建两条消息。这些取舍我都能讲清楚。

**关键词**：独立实现 + 每个取舍都能讲清

> 面试官真正在意的不是"是不是你敲的"，而是**你懂不懂**。说"我实现的"然后被追问细节答不上来，比说"我跟着课程实现但做了扩展"危险十倍。

### Q6. 用户问一句话之后，ChatAgent 怎么判断接下来做什么？

**⭐ 这题必考，背熟。**

**60 秒版**

> 分四步。
>
> **第一步，四步准备**：先压缩上下文腾空间，再把用户消息写库，然后重建证据快照，最后组装上下文。**顺序不能反**——先写消息再压缩，刚插的消息会被当旧消息压掉。
>
> **第二步，四道短路**：能用规则答的不进 LLM。"我刚才说了什么"直接读最近消息；点名了记忆工具就直接预取；问项目概况就预读 README；没配 LLM 就用证据拼答案。
>
> **第三步，进 LangGraph 循环**。图里只有两个节点：`model_decision` 问模型"要不要调工具"，`tool_action` 执行一个工具，然后回到决策。最多 12 步。
>
> **第四步，收尾**：没答案就给降级答案，然后把整轮结果落库。

**关键词**：四步准备 → 四道短路 → 两节点循环 → 收尾落库

**追问**：怎么判断"要不要调工具"？→ 不是规则判断，是模型原生 tool calling。我在 system prompt 里给了 14 个工具的说明和选择规则，模型返回 `tool_calls` 就执行，返回文本就是最终答案。

### Q7. Function Call 具体怎么执行的？

**60 秒版**

> 五步。
>
> **① 工具声明**：14 个工具转成 LangChain 的 `StructuredTool`，每个带 Pydantic schema，模型看到的是结构化的参数定义。
> **② 模型决策**：`ainvoke` 一次调用，模型返回 `tool_calls` 数组，里面有工具名、参数、调用 ID。
> **③ 参数清洗**：模型经常漏参数——忘了传 `query` 就拿用户原话兜底，忘了 `repo_id` 就由服务端注入。
> **④ 执行**：一次只执行一个（`pending[0]` 出队），这样前端能逐个显示"正在调第 2 个工具"。
> **⑤ 回灌**：工具返回四件套 `{route, tool_calls, answer, citations}`，`answer` 进观察结果，下一轮拼进 prompt。
>
> 关键点：**结果不是 append 到消息列表，而是拼进下一轮的 user prompt 字符串**。

**关键词**：声明 → 决策 → 清洗 → 单个执行 → 回灌 prompt

**追问**：为什么一次只执行一个？→ 并行执行会丢过程。用户看不到中间发生了什么，出错了也不知道是哪一步。

### Q8. 为什么用 LangGraph，不自己写 while 循环？

**30 秒版**

> 因为**状态管理和中断恢复**。
>
> 自己写 while 循环，状态散在局部变量里，加一个"步数超限兜底"就得改循环条件，加"重复调用检测"又要插一段，很快就乱了。
>
> LangGraph 是显式的状态图：三个节点、两条条件边，状态是一个 TypedDict 在节点间传。加节点就是加一个函数，加分支就是加一条条件边。而且它自带递归保护和 `stream_mode="debug"`，能拿到每个节点的输入输出——我用这个来推 `tool_use` 事件。

**关键词**：显式状态图 / 加节点不改循环 / debug 模式拿事件

**追问**：LangGraph 有什么缺点？→ 抽象层多，调试时栈很深；简单场景不如直接写循环直观。**别只说优点，说一个缺点显得你真的用过。**

### Q9. 讲一下 RAG 的完整流程

**60 秒版**

> 两条链路。
>
> **入库**：文件上传 → 解析（PDF/DOCX/Markdown）→ 结构感知切片（父子块）→ 向量化 → 写 Milvus + 落 `documents` 表。状态是 `queued → parsing → splitting → embedding → completed`，前端轮询进度。
>
> **查询**：问题进来 → 向量召回 + BM25 关键词召回 → 加权融合（0.62/0.30，双路都命中加 0.08）→ 去重 → 父块占用限制（同一父块最多留 2 片）→ Rerank → 证据压缩 → 准入判断 → 生成带引用的回答。

**关键词**：入库五阶段 / 查询六步 / 0.62-0.30 / 父块最多 2 片

### Q10. 为什么向量和关键词两路都要做？

**30 秒版**

> 因为两者互补。
>
> 向量懂语义——"登录失败"能匹配到"认证报错"。但它对精确标识符很差，`auth_service.py` 这种它可能召回不到。
>
> BM25 正好相反，精确匹配很强，但不懂同义词。
>
> 所以两路都跑，加权融合。**而且这是降级设计**：Milvus 挂了，hybrid 自动退化成纯关键词，对话不中断；如果只用向量，向量库一挂就彻底废了。

**关键词**：语义 vs 精确 / 互补 / 降级不中断

---

### Q11. 多轮对话和上下文怎么管？

**60 秒版**（这题你能讲得比大多数人深，重点展开）

> 三层。
>
> **第一层，最近消息**：直接取最近 N 条原文。
> **第二层，历史摘要**：更早的对话压成摘要，存成一条 `role=system` 的假消息当压缩边界。
> **第三层，长期记忆**：对话封存时抽取候选记忆，人工确认后进知识库，下次能检索到。
>
> 组装时按预算分配，token 快满了触发两级压缩：先 `microcompact` 只清旧的工具结果，不够再 `compress_messages` 丢旧消息。
>
> 还有一个关键设计：**每轮只重建 System + Human 两条消息**，历史全拼进 user prompt 字符串。这样 token 消耗可预测，不会聊 50 轮就撑爆。

**关键词**：三层 / 两级压缩 / 每轮只两条消息

**追问**：摘要和最近对话谁放前面？→ 最近对话在后面（靠近用户原话），因为模型对末尾内容最敏感。

### Q12. 怎么防幻觉？

**60 秒版**

> 四道。
>
> **① 证据门槛**：检索完先过 answer gate，判断证据够不够。不够就回"证据不足，需要补充范围"，而不是硬编。
> **② 强制引用**：答案里的 `[1][2]` 由后端统一发号，对应具体的 chunk。
> **③ 硬规则断言**：评测时检查"该出现的关键事实有没有出现、不该出现的有没有出现"，不通过就判失败。
> **④ 提示词约束**：明确要求"涉及源码必须先读工作区文件"、"负责人只能从团队成员列表里选"。

**关键词**：准入闸门 / 强制引用 / 硬规则 / prompt 约束

## §2 技术深挖 10 题

### Q13. 模型选错工具、参数填错、重复调用同一个工具，怎么办？

**三道刹车 + 三道校验**

> **决策阶段**：同一工具同一参数指纹超过 2 次，直接停，返回"我停止了这轮循环，继续只会重复消耗预算"。
> **执行前**：① 技能白名单校验——激活了某个 Skill，就只能用它声明的工具，越界返回 `permission_denied`；② 工具存在性校验——不存在就把可用工具列表回给模型，让它自己改。
> **执行中**：错误分类。只有超时和 429 限流重试 1 次，参数错、权限错不重试——重试一万次也没用。
> **兜底**：12 步用完还没答案，用已有证据给降级答案，告诉用户"查到什么、还差什么"。

**关键词**：2 次指纹 / 白名单 / 分类重试 / 12 步降级

### Q14. 上下文超了怎么办？

> 两道防线。
>
> **事前**：每轮开始先 `ensure_headroom`，快满了提前压缩。
> **事后**：真触发了 `context_length_exceeded`，用 `aggressive` 模式重建 prompt 重试一次——服务端上下文压到 1/3，历史压到 1/2。
>
> **只重试一次**。无限重试会变死循环。而且重试前打标记，防止嵌套重试。

**关键词**：事前压缩 / 事后一次激进重试 / 打标记防嵌套

### Q15. 多个 Agent 怎么并行？上游失败怎么办？结论冲突听谁的？

**⭐ 三个子问题，分开答**

> **并行**：按依赖拓扑执行。先找依赖全部完成的任务进 ready 队列，按 `max_parallel_tasks` 分批 `asyncio.gather` 并发跑。
>
> **上游失败**：级联跳过，不硬跑。依赖失败的任务直接标 `skipped`，不执行。而且如果 pending 里一个 ready 都没有，说明依赖成环或引用了不存在的任务，全部标 error。
>
> **结论冲突**：靠 Observer 做确定性检查，不是让 LLM 投票。它跑 6 类检查：任务状态、证据缺失、置信度过低、合入门禁、负责人可信度、写操作是否需人工确认。
>
> 置信度是算出来的：各任务平均分，减 0.2×blocker 数、减 0.05×warning 数，夹在 0.1~0.95 之间——**再差也留一点，再好也不给满分**，避免过度自信。
>
> 有 blocker 或 spec 要求人工确认，就必须人工复核。

**关键词**：拓扑 + 分批 gather / 级联跳过 / 6 类检查 / 0.2-0.05 扣分 / 0.1-0.95 夹紧

### Q16. 为什么写操作必须先生成草稿？

> 因为**AI 不能产生不可逆的副作用**。
>
> 四段式：草稿 → 权限校验 → 人工确认 → 审计。状态机是单向的：`pending_confirmation → executed / cancelled / failed`，没有回退接口。
>
> 两个细节：
> ① **权限分两级**，能创建草稿和能批准执行不是同一批人。
> ② **失败也写审计**——执行失败不抛异常，落 `status=failed` + 错误原因 + 一条 failed 审计。否则用户不知道为什么没成功。

**关键词**：四段式 / 状态机单向 / 权限两级 / 失败也审计

---

### Q17. 为什么源码不放进向量库？

> 这是刻意的分流规则。
>
> 三类数据三种走法：文档和 Issue/PR 进 RAG；结构化事实（状态、时间、负责人）直接查表；**源码两边都不进**。
>
> 原因有两个：
> ① 源码有精确结构，符号、调用关系用 grep 和代码图谱查比语义检索准得多；
> ② 代码天天改，向量会过期——今天索引的 `chat_agent.py`，明天就变了，检索到的是旧代码。
>
> 所以源码走工作区实时读 + 代码图谱，永远是最新的。

**关键词**：三类分流 / 精确结构用 grep / 向量会过期

> 💡 这题是**差异化加分题**，模板里没有。答好了显得你真想过。

### Q18. 文档怎么切？chunk size 和 TopK 怎么定？

> **切法**：结构感知，不是按固定字数硬切。先按标题层级切，再按自然段落切，过长段落才按长度拆。
>
> **父子块**：小块用来检索（准），命中后用 `parent_id` 拼回大块（全）。**用小的命中，用大的回答**。
>
> **参数**：默认 chunk size 几百字符、overlap 几十字符，TopK 默认 5，可调 3/5/8/10。
>
> **为什么 overlap 不能大于等于 chunk size**：会原地打转无限切，所以保存时直接禁用。

**关键词**：结构感知 / 父子块 / 小的命中大的回答 / overlap < size

**追问**：参数调过吗？→ **诚实答**：用的是经验默认值，没做过系统的参数扫描。如果要调，我会固定评测集，扫 size ∈ {256,512,1024} × TopK ∈ {3,5,8}，看 Recall@K 和 Faithfulness 的变化。

### Q19. 知识库里明明有答案，为什么还是没答对？怎么排查？

> 按检索流水线倒着查，前端有 trace 面板，每一步的数量都记着。
>
> ① **切片问题**：答案被切断了，看 chunk 内容确认。
> ② **召回没命中**：向量和 BM25 都没捞到，看 trace 里召回数量。
> ③ **被阈值筛掉**：召回了但分数低于门槛，看 score。
> ④ **被准入闸门拒了**：证据不够，看 answer_gate 的 reason。
> ⑤ **证据够但生成跑偏**：看 Faithfulness 分数，这是模型没忠于证据。
>
> **先看 trace 再改 Prompt**——大部分人一上来就改 Prompt，其实问题在检索。

**关键词**：切片 → 召回 → 阈值 → 闸门 → 生成，倒着查

### Q20. 怎么评测？改完 Prompt 怎么知道有没有变好？

> **两层**。
>
> **RAGAS 语义分**：Context Precision / Recall / Faithfulness / Answer Relevancy / Agent Goal 五项。能测质量，但会飘——同一个答案两次打分可能不一样。
>
> **硬规则断言**：8 项确定性检查——来源是否命中、有没有证据、有没有答案、格式对不对、工具有没有报错、关键事实在不在、禁用事实有没有出现。可复现，但只测对错。
>
> **关键是**：硬规则不过 = 一定失败，不管 RAGAS 多少分。
>
> **对比要可比**：题库 hash、RAGAS 版本、Judge 模型、TopK 四项必须一致，不一致就明确拒绝当严格对照。

**关键词**：语义分 + 硬规则 / 硬规则一票否决 / 四项可比性

**追问**：大模型打分靠谱吗？→ 不完全靠谱，所以我只用它做**相对比较**，不用它做绝对判定。绝对判定交给硬规则。

---

### Q21. 为什么用 SSE 不用 WebSocket？

> 因为**单向就够了**。
>
> 这个场景是服务端推、客户端听：token 增量、工具调用状态、任务进度。用户要发消息，走普通 POST 就行。SSE 基于 HTTP，不用握手升级，断线自动重连，代理和网关都友好。
>
> WebSocket 是双向的，这里用不上，反而多一套连接管理。

**关键词**：单向够用 / HTTP 原生 / 自动重连

---

### Q22. MCP、Tool、Skill 有什么区别？

> **Tool** 是能力本身，一个函数。
> **MCP** 是工具的**接入协议**——把工具做成独立进程，通过 JSON-RPC 暴露，好处是可以跨语言、跨进程复用。我项目里记忆工具就是走 MCP 的 stdio 服务。
> **Skill** 是**做事的套路**——一个 Markdown 文件，写明这类任务该按什么步骤、用什么工具、输出什么格式。
>
> 一句话：Tool 是手，MCP 是插座，Skill 是作业指导书。

**关键词**：手 / 插座 / 指导书

> 💡 这个比喻很好用，面试官通常会笑一下，气氛会松。

## §3 压力面 5 题

> **总原则：先投降，再引导。** 压力面考的是抗压，不是知识。

### Q23.「你这个项目看起来很简单，都是常见方案吧？」

> 面试官您是专家，这些方案确实都是业界常见的。但对我来说真正的挑战在**细节**——比如怎么让 Agent 不空转、怎么在有限 token 里保住关键证据、怎么防止模型编造一个不存在的负责人。
>
> 我举个具体的：一开始 Agent 会反复调同一个工具，因为模型觉得"再查一次可能更全"。我加了参数指纹检测，同工具同参数超过 2 次直接停。这类问题方案书上不会写，只能自己踩。

**关键词**：先认同 → 转到细节 → 给一个真实踩坑

---

### Q24.「你们这个项目的 TPM / QPS 是多少？」

> 这个我没测过。这是个内部工具定位的项目，不是面向大量用户的 C 端服务，所以还没做过压测。
>
> 我能说的是单次请求的链路耗时分布——检索、LLM 调用、工具执行各占多少，这个我在 trace 里有记录。如果要压测，我会先用 locust 打接口，重点看 LLM 调用的并发瓶颈。

**关键词**：没测过 → 说明定位 → 给替代指标 → 给压测方案

> ❌ 绝对不要编一个数。编了会被追问"怎么压的、瓶颈在哪"，必崩。

---

### Q25.「这个项目最难的地方是什么？」

> 最难的不是写代码，是**决定什么时候不让 AI 自己决定**。
>
> 比如"要不要调工具"交给模型，但"能不能改 GitHub"绝对不能交给模型。所以我把能力切成了两半：读操作让 Agent 自由发挥，写操作必须走草稿 + 人工确认。
>
> 另一个难点是**上下文预算**。既要保住最近对话，又不能丢掉三天前的决策。我最后做成分层 + 两级压缩，但中间试过几个版本，早期版本会把关键证据压掉，导致答案突然变差。

**关键词**：什么时候不让 AI 决定 / 读写分离 / 上下文预算

---

### Q26.「如果继续做，你会怎么改？」

> 三个方向。
>
> ① **评测**：现在评测集是固定的几十道题，覆盖面不够。我想按失败类型自动生成新题——用户点差评的那些 case，应该自动变成评测题。
> ② **检索**：现在融合权重是拍的经验值，想做参数扫描 + 学习排序。
> ③ **并发**：现在是单机 uvicorn，多 Agent 并行靠 `asyncio.gather`，真上量要换成任务队列。

**关键词**：评测自动出题 / 权重调优 / 任务队列

> 💡 说"我会怎么改"时，**要能说出为什么现在没做**（时间、优先级），否则显得是没想到。

---

### Q27.「你觉得这个项目有什么不足？」

> 三点，我都很清楚。
>
> ① **没做压测**，不知道并发上限。
> ② **前端没有自动化测试**，23 个 TS 文件全靠手测。
> ③ **多租户没做**，现在是按 `repo_id` 隔离，但用户权限只有两级，真正的多租户要加行级权限。

**关键词**：没压测 / 前端无测试 / 无多租户

> 主动说不足 + 说清边界，比被追问出来强得多。

## §5 三个"千万别这么说"

| 别这么说 | 为什么 | 改成 |
|---|---|---|
| "我从 0 到 1 设计了整个系统" | 除非真的一行行写的，否则追问三个细节就崩 | "我独立实现了全链路，每个取舍都能讲清" |
| "我的 Agent 准确率 95%" | 没有基线，也没有留档 | "硬规则通过率 X%，RAGAS 各项在 Y 左右"（说得出才算） |
| "这个方案是业界最佳实践" | 空话，且暗示你没想过替代方案 | "我选它是因为 A；如果换成 B，代价是 C" |

**另外**：不要说"精通"。学生项目说精通，面试官一定会往死里问。
